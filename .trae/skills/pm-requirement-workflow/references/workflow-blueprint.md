# AI 辅助 PM 需求工作流总蓝图

## 工作流定位

这套工作流用于帮助 PM 将零散、口语化、不完整的业务输入，转成可讨论、可评审、可开发、可测试的需求材料。核心目标是提升需求分析、PRD、HTML 高保真原型、逆向检查和验收前置的质量。

这不是审批流程，也不是完整产品经营闭环。主流程不包含范围收缩和上线复盘。

## 主流程

1. 需求入口确认
2. 资料整理
3. 需求澄清
4. 价值评估
5. 方案建模
6. PRD 生成
7. HTML 高保真原型
8. PRD 逆向检查
9. 验收前置

## 需求模式

需求模式由用户指定，Codex 不主动裁决。

| 模式 | 适用情况 | 工作重点 |
|---|---|---|
| 轻量 | 字段、文案、筛选、按钮、页面小调整 | 快速整理、提醒影响面、输出验收标准 |
| 标准 | 新页面、新功能、新流程、常规后台模块 | 跑完整主流程 |
| 复杂 | 供应链、财务、税务、审计、多系统、多角色、多状态、多数据口径 | 强化权限、数据、合规、异常、验收 |

如果用户指定的模式可能低估复杂度，只做风险提醒，不替用户升级模式。复杂度信号包括审批、权限、金额、税率、发票、对账、结算、库存、采购、供应商、多系统、历史数据、审计留痕、财务或税务合规。

## 模块定义

| 模块 | 目标 | 主要产物 |
|---|---|---|
| 需求入口确认 | 快速确认需求基本信息和处理模式 | 需求入口卡 |
| 资料整理 | 把会议、聊天、口头反馈整理成可分析上下文 | 背景摘要、已知信息、业务诉求、AI 推测、待确认问题 |
| 需求澄清 | 反问关键问题，避免直接写方案 | 澄清问题清单、待确认风险 |
| 价值评估 | 分析为什么值得做，对哪些对象有价值 | 供应链价值、业务价值、公司价值、员工价值、用户价值、风险控制价值 |
| 方案建模 | 在写 PRD 前想清业务流程、权限、数据、状态、异常 | 方案建模卡 |
| PRD 生成 | 把需求整理成可评审、可开发、可测试文档 | PRD 草稿或 PRD 评审版 |
| HTML 高保真原型 | 把需求变成可点击、可讨论、可分享的后台界面 | 单文件评审原型，或 GitHub Pages 静态站点文件夹 + ZIP + 首页预览；交互说明、PRD 反向问题 |
| PRD 逆向检查 | 像评审人一样挑问题 | 风险问题清单、修改建议 |
| 验收前置 | 把需求转成可测试、可验收、可上线检查内容 | 验收标准、测试用例、上线检查清单、操作手册草稿 |

## 需求入口卡字段

| 字段 | 说明 |
|---|---|
| 需求名称 | 用一句话描述需求 |
| 需求模式 | 轻量 / 标准 / 复杂，由用户指定 |
| 需求来源 | 业务方、老板、运营、财务、供应链、客服、数据反馈等 |
| 目标摘要 | 希望解决什么问题 |
| 影响对象 | 用户、角色、部门、系统、流程 |
| AI 风险提醒 | 是否存在复杂度被低估的信号 |

## 各模式裁剪

| 模块 | 轻量 | 标准 | 复杂 |
|---|---|---|---|
| 需求入口确认 | 必须 | 必须 | 必须 |
| 资料整理 | 简化 | 标准 | 完整 |
| 需求澄清 | 3-5 个问题 | 8-12 个问题 | 12 个以上，含合规/供应链 |
| 价值评估 | 简化 | 标准 | 完整 |
| 方案建模 | 只看改动点和影响面 | 完整 | 强化系统、合规、审计 |
| PRD 生成 | 轻量需求说明 | 完整 PRD | 完整 PRD + 合规章节 |
| HTML 原型 | 可选，局部页面 | 页面型需求建议做 | 通常必须做 |
| PRD 逆向检查 | 5-8 个风险 | 至少 10 个问题 | 至少 15 个问题 |
| 验收前置 | 验收标准为主 | 验收 + 测试用例 | 完整验收 + 测试 + 上线检查 + 手册 |

## 强规则

1. 资料整理不做通过标准，也不阻塞后续流程。
2. 价值评估不做卡控，只用于帮助 PM 表达价值。
3. 不设置范围收缩模块，不主动规划一期、二期、三期。
4. 不设置上线复盘模块；上线后数据反馈可作为可选动作，但不进入主流程。
5. 必须区分已确认内容、AI 推测内容、待确认内容。
6. PRD 只写本次需求，不主动扩大范围。
7. HTML 原型必须遵循 Element Plus + Vue 3 企业后台设计规范。
8. 新建快速评审原型可使用包含 CSS、JS 和 mock 数据的单文件 HTML；现有原型版本迭代、多页面或 GitHub Pages 发布需求默认交付纯静态多文件站点。
9. GitHub Pages 交付必须保持用户指定的目录与 URL 结构，使用相对路径，不额外套版本目录，并提供完整文件夹、同内容 ZIP 和首页预览。
10. HTML 原型必须可点击，有动态交互；静态页面不算完成。
11. 做完 HTML 原型后，必须逐页验证页面、样式、脚本、导航和核心交互，并输出版本修改清单、上传/替换文件清单以及原型反向发现的 PRD 问题。
12. PRD 逆向检查先挑问题，不直接替用户改需求范围。
13. 验收标准必须可测试，不能写"体验友好"这类虚描述。

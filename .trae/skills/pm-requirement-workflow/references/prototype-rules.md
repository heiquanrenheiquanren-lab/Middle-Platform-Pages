# HTML 高保真原型规则

## 定位

HTML 高保真原型不是最终前端代码，也不是视觉设计稿。它用于把 PRD 中的页面、流程、字段和交互快速变成可点击、可评审、可讨论的界面样稿。

核心价值是把文字争议变成界面争议，并反向暴露 PRD 中的字段、交互、权限、状态和异常问题。

## 何时需要原型

| 情况 | 是否建议做 |
|---|---|
| 字段、文案、小按钮调整 | 可选 |
| 新页面、新列表、新表单、新弹窗 | 建议做 |
| 多角色、多状态、多流程 | 必须做 |
| 审批、对账、结算、库存、供应链流程 | 强烈建议做 |
| 纯后台规则、接口逻辑、定时任务 | 可用流程图或规则表替代 |

## 交付模式判断

根据用户意图选择，不要把两种模式混在一次交付中：

| 模式 | 适用情况 | 默认交付 |
|---|---|---|
| 单文件评审模式 | 新建快速原型、局部页面评审，或用户明确要求单文件 | 一个内联 CSS/JavaScript 的完整 `.html` |
| GitHub Pages 交付模式 | 基于现有 HTML 原型进行版本迭代、多页面原型，或用户要求上传、共享、发布到 GitHub Pages | 可直接上传到仓库根目录的完整静态文件夹 + 同内容 ZIP + 首页预览链接 |

## 通用强制要求

1. 必须使用纯静态 HTML、CSS 和 JavaScript。
2. 必须直接在浏览器打开即可运行，不依赖安装、编译或启动服务。
3. 必须遵循 Element Plus + Vue 3 企业后台设计规范。
4. 页面风格必须简洁、专业、信息层级清晰。
5. 必须使用 mock 数据，不需要真实后端接口。
6. 必须有动态交互，静态页面不算完成。
7. 关键操作必须可点击，操作后页面状态必须变化。
8. 必须有表单校验、操作成功/失败反馈、空状态或异常提示。
9. 中文文案要自然，适合真实业务系统。
10. 页面适合电脑端后台使用，不优先做移动端。
11. 不做花哨视觉风格，保持企业后台克制专业。

## GitHub Pages 交付模式强制要求

1. 把用户指定的目录结构视为交付合同；如果用户未指定，先根据现有页面和 GitHub Pages 路径推导最小必要结构。
2. 仓库根目录必须直接包含 `index.html`、`app.js`、`styles.css` 和用户指定的子目录。
3. 不要在最外层额外套 `vX.X.X/`、`dist/`、`build/` 或项目名文件夹。
4. 每个页面目录默认包含 `index.html`、`app.js`、`styles.css`，除非用户给出不同结构。
5. 所有内部页面、样式、脚本、图片和字体必须使用相对路径；禁止 `/Users/...`、`file://...` 和以 `/` 开头的站点根路径。
6. 必需资源优先包含在交付文件夹中。仅可对非必需资源使用稳定 CDN，并确保 CDN 失效不会让核心流程不可用。
7. 左侧导航必须在所有页面保持一致，使用真实相对链接切换页面，并保持现有 GitHub Pages URL 结构。
8. 版本号必须使用用户提供的 `vX.X.X`；不自行猜测或递增。如果未提供，在交付说明中标记待确认。
9. ZIP 必须与交付文件夹内容一致；ZIP 解压后的第一层就是 `index.html`、`app.js`、`styles.css` 和 `pages/`，不得多一层包装目录。

用户指定如下结构时，必须原样保持：

```text
index.html
app.js
styles.css
pages/
  stock-plan/
    index.html
    app.js
    styles.css
  purchase-plan/
    index.html
    app.js
    styles.css
  shipment-plan/
    index.html
    app.js
    styles.css
  purchase-orders/
    index.html
    app.js
    styles.css
```

## Element Plus + Vue 3 风格落地

| 场景 | 组件风格 |
|---|---|
| 页面布局 | el-container、el-aside、el-header、el-main |
| 查询区 | el-form（inline 属性）/ compact filter |
| 数据列表 | el-table + el-pagination |
| 状态展示 | el-tag |
| 重要提示 | el-alert |
| 新增 / 编辑 | el-dialog 或 el-drawer |
| 详情查看 | el-drawer / el-descriptions |
| 流程展示 | el-steps / el-timeline |
| 操作确认 | el-popconfirm / ElMessageBox.confirm |
| 操作反馈 | ElMessage |
| 多页面切换 | el-tabs |
| 批量操作 | el-table selection + el-button 工具栏 |

GitHub Pages 交付模式下，使用 Vue 3 + Element Plus 的 CDN 引入方式（`vue.global.prod.js` + `element-plus.js` + `element-plus.css`），放在 `vendor/` 目录中供所有页面共享。

## 动态交互要求

根据需求选择合适交互，至少覆盖核心路径：

1. 查询筛选：输入条件后能刷新列表或展示筛选结果。
2. 分页：页码或每页条数可切换。
3. 新增：点击新增打开弹窗/抽屉，填写后能新增 mock 数据。
4. 编辑：点击编辑带出当前行数据，保存后列表变化。
5. 查看：点击查看打开详情弹窗/抽屉。
6. 删除 / 作废 / 停用：点击后有确认，确认后状态或列表变化。
7. 状态流转：提交、审核、驳回、撤回、确认等操作能改变状态。
8. 表单校验：必填、金额、数量、日期等要有校验提示。
9. 反馈提示：操作成功/失败要有 message 或 alert。
10. 角色切换：如果涉及权限，要能切换角色并展示按钮/数据差异。
11. 空状态 / 异常：无数据、权限不足、校验失败要有可见效果。

## 不应该做

1. 不追求真实后端接口。
2. 不追求最终前端代码质量。
3. 不做复杂权限系统，只用 mock 角色切换表达。
4. 不做完整数据计算，只模拟关键结果。
5. 不主动扩展 PRD 没有定义的功能。
6. 不使用花哨营销页风格。

## 输出要求

单文件评审模式：
1. 先简要说明原型包含哪些页面、弹窗或抽屉。
2. 输出完整 HTML 代码或直接创建 `.html` 文件。
3. HTML 代码必须完整，不要省略。
4. 不依赖真实接口。
5. 可使用内联 CSS 和原生 JavaScript。
6. 如需图标，优先用 CSS、文本或简单字符，不依赖无法保证加载的外部资源。
7. 完成 HTML 后，输出"原型反向发现的 PRD 问题"。

GitHub Pages 交付模式：
1. 先检查现有原型、用户指定的目录树、现有 URL 路径和版本号。
2. 在交付目录内直接创建全部文件，不留空文件、占位文件或省略代码。
3. 对每个 HTML 文件检查其 CSS、JavaScript 和导航相对路径是否能从当前层级解析。
4. 在浏览器逐页验证首页、所有子页、左侧导航、样式、脚本和核心交互；同时检查控制台错误和缺失资源。
5. 扫描交付文件，确认不含本地绝对路径、`file://`、本地服务地址或未说明的站点根路径。
6. 从交付目录内容创建同内容 ZIP，并复核 ZIP 的顶层结构。
7. 交付时必须同时提供：完整文件夹链接、ZIP 链接、根目录 `index.html` 预览链接、版本号、本次修改清单、需上传或替换的文件清单、验证结果。
8. 完成后输出"原型反向发现的 PRD 问题"。

## GitHub Pages 交付前检查清单

- [ ] 根目录直接包含 `index.html`，没有额外版本文件夹。
- [ ] 用户要求的每个页面和文件都存在。
- [ ] 本地双击根目录 `index.html` 可运行。
- [ ] 首页与所有子页的 CSS 和 JavaScript 均已加载。
- [ ] 所有左侧导航链接可到达正确页面，当前页高亮正确。
- [ ] 核心交互、表单校验、状态变化和反馈正常。
- [ ] 不存在本地绝对路径、`file://` 或不必要的本地服务依赖。
- [ ] ZIP 与文件夹内容一致，解压后没有多一层目录。
- [ ] 交付说明包含版本号、修改清单和需上传/替换的文件。

## 原型反向发现的 PRD 问题

输出格式：

| 问题 | 为什么重要 | 建议补充到 PRD 的位置 |
|---|---|---|

常见发现包括：
- PRD 没写某个按钮点击后去哪。
- 字段太多，页面放不下。
- 状态下操作冲突。
- 权限没有定义清楚。
- 列表和详情字段不一致。
- 异常提示没有规则。
- 原型交互暴露出 PRD 中缺少确认、退回、作废、日志等规则。

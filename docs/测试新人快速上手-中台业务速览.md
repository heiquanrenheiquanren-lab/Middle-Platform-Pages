## 一、一句话理解中台

供应链中台把**商品、供应商、库存、计划、采购、物流**串成一条可追踪的链路：把销售需求变成采购和发货计划，再把计划变成真实单据，最后把货和成本收回来。

一句话记住它的四个目标：**计划可执行、库存可追踪、口径统一、过程可追溯**。

---

## 二、业务全景

```
基础资料（商品SKU / 供应商 / 仓库 / 平台店铺）
        ↓
需求预测 → 备货计划 → 采购计划 → 采购单 → 供应商库存
                        ↓
                   发货计划 → 发货单 → 平台仓 / 海外仓库存
                                 ↓
                            成本 · 费用 · 对账
```

| 层级 | 模块 | 定位 | 产出 |
|---|---|---|---|
| 基础 | 基础资料 | 主数据与编码映射，被所有模块引用 | SKU、供应商、仓库、店铺 |
| 计划层 | 需求预测 | 按月维护销量预测 | 预测单 → 备货需求 |
| 计划层 | 备货计划 | 需求 − 库存 − 在途 = 建议备货量 | 备货计划 → 采购方案 |
| 计划层 | 采购计划 | 按供应商拆成可下单的采购方案（组合品拆子件） | 采购计划 → 采购单 |
| 计划层 | 发货计划 | 采购完成后的物流安排（从哪发、到哪、走什么渠道） | 发货计划 → 发货单 / FBA货件 |
| 执行层 | 采购单 | 采购执行主单：推送 ERP、审批、收货、货权调整 | 供应商库存 + 收货批次 |
| 执行层 | 发货单 | 履约执行单：提货 → 加工 → 发货 → 收货 | 目的仓库存 + 履约批次 |
| 执行层 | FBA货件 | 领星同步来的货件，与发货计划做关联 | 计划执行交接完成 |
| 支撑 | 供应商库存 / 调拨单 / 库存查询 / 库存流水 | 货在哪、属于谁、放了多久 | 库存状态与库龄 |
| 支撑 | SKU 单位头程成本 / 头程费用 | 每批货的物流与采购成本 | 成本与对账口径 |

**读法建议**：按"计划 → 采购 → 库存 → 物流"的顺序理解，不要从单个页面切进去看。

## 三、核心业务逻辑（重点）

### 1. 计划层与执行层的分界

计划只形成"安排"，不动库存；单据才产生真实业务结果。

- 计划层（预测/备货/采购/发货）：只做数量、日期、供应商、仓库、渠道的安排。
- 执行层（采购单/发货单）：产生在途、在库、批次、成本和日志。
- 关键理解：**计划的状态"已完成"≠ 货已经到了**，它只代表"这条计划已经交接给下游单据"。

### 2. 两条并行的履约链路

| 链路 | 适用 | 流转 |
|---|---|---|
| 普通链路 | 非亚马逊平台/店铺 | 发货计划（待发货）→ 中台发货单 → 提货/加工/发货/收货 → 目的仓库存 |
| FBA 链路 | 亚马逊团队 | 领星同步 FBA货件 → 与发货计划关联 → 计划状态转「已完成」，后续以货件数据为准 |

两条链路互斥：亚马逊的发货计划**不进入**中台手动新建发货单流程。关联是双向入口（货件侧选计划、计划侧填货件号），操作的是同一份关联关系，校验和状态规则必须一致。

### 3. 三个状态机（测试最常踩的坑）

**采购单：中台只做前半段，审批在外部 ERP**

```
待提交（中台本地，未推送）
  → 提交审核推送易仓/领星 → 待审批
  → ERP 内部提交+审核 → 中台每 10 分钟自动同步（或手动刷新）
  → 待收货 →（收货）→ 部分收货 → 已完成
  推送失败/审核拒绝 → 回待提交；ERP 撤销/删除 → 已作废
```

要点：**待提交**是本地态，**待审批**才是已推送成功态。任何一个环节失败，都要能回到可重试的状态。

**发货单：状态是"单据维度"的**

```
草稿 → 待提货 →（普通SKU或仅成品提货）→ 待发货 → 待收货 → 部分收货 → 已完成
              →（存在子件套装提货）→ 待加工 → 待发货
        → 取消发货 → 已取消；草稿 → 已作废
```

要点：只要一张单里发生**子件套装提货**，整张单必须先进「待加工」，加工是单据级动作，不是单个 SKU 的状态。少提、少发、少收不新增流程，只用差异数量和原因记录。

**发货计划**

```
待确认 → 待发货 →（已关联发货单 / 已关联FBA货件）→ 已完成
                 → 运输中 → 已完成
        → 已作废
```

要点：发货计划的「待发货」和发货单的「待发货」**含义完全不同**，测试造数据时极易混淆。

### 4. 发货单的库存流转（8 条口径）

| 动作 | 库存变化 |
|---|---|
| 创建 / 作废 / 取消（待提货） | 不动库存，只处理计划关联与状态 |
| 提货 | 扣提货仓、增发货仓；组合子件按 BOM 配比落到子 SKU，可跨仓 |
| 物流加工 | 扣发货仓子 SKU、增发货仓组合 SKU |
| 发货 | 扣发货仓、增海外在途 |
| 收货 | 扣海外在途、增目的仓库存 |
| 手动完成 | 直接扣掉剩余在途，**不增**目的仓库存 |
| 数量调整 | 按原路径回滚（提货/发货/收货各管各的区间） |

原则：**任何库存增减都要能对上一条业务动作**，且重复操作不能重复扣（幂等）。

### 5. 库存的三个维度与团队库存口径

- **数量**：实际有多少。
- **物流状态**：供应商仓 / 在途 / 在库 / 已出库。
- **货权归属**：属于哪个团队/平台/店铺。货权调整不等于实物移动。

```
团队可售库存 = 发货单实际收货形成的库存 − 销售订单占用 / 出库
             ± 后续入库、退货、调整
             → 最终以 ERP（易仓/领星）同步的实际库存快照校准
```

## 四、不能违反的刚性规则

| 规则 | 位置 |
|---|---|
| 同一发货单必须同一目的仓 | 新建发货单 |
| 亚马逊相关的单不在中台手动创建（选项置灰） | 新建发货单 |
| 一个发货计划只能关联一张发货单（草稿保存即锁定） | 发货单提交 |
| 新增 SKU 只能选「待发货」且未关联的计划 | 发货单 |
| 加工数量 ≤ 已提子件套装数量，且不超过可加工上限 | 物流加工 |
| 发货计划可关联的前提是「待发货」 | 发货计划 / FBA货件 |
| 已关联 FBA 货件的计划不可作废、不可再生成发货单 | 发货计划 |
| 外部 ERP 异常时中台保留单据、批次和日志，供人工核对 | 采购单 |

## 六、当前项目形态（测试必知）

- 这是**纯静态 HTML 交互原型**，没有真实后端，数据全部是页面内 mock。
- 刷新页面 = 数据回到初始态；跨页面"关联"只在本页内存生效。
- 主要页面各有固定模拟数据量（如发货计划 62 条、发货单 33 条），便于批量与分页测试。
- 各页共用统一导航与 UI 骨架，筛选维度、状态页签、行内编辑、导出等交互模式高度一致——**一个页面里的交互 bug 往往在其他页面同样存在**。

## 七、测试切入建议（按顺序）

1. **跑通主链路**：需求预测 → 备货 → 采购计划 → 采购单 → 发货计划 → 发货单，确认每一步的上下游单号能对上。
2. **验证状态机**：每条流转画一遍，重点测"非法流转是否被拦住""失败后能否重试"。
3. **验证库存账**：每个履约动作前后对比库存，验证 8 条口径；重复操作测幂等。
4. **验证关联冲突**：同一计划被两个单据/两个用户同时关联；已关联后再作废；解除关联后库存不回滚。
5. **验证外部协同**：ERP 推送失败、审核拒绝、撤销/删除、同步延迟 10 分钟内的中间态。
6. **最后测页面交互**：筛选、多选、分页、行内编辑、导出、弹窗校验、空态。

## 八、已知边界与待确认事项（不要当 Bug 提）

| 主题 | 现状 |
|---|---|
| FBA 库存 | 自闭环计算（初始化在库/在途 ± 累计签收量），本期不拉实时库存、不纠错 |
| FBA 关联动作 | 关联/解除关联**不影响**库存，库存只由签收量驱动 |
| 货权调整 | 哪些场景允许调整在途/发货单货权，尚未最终确认 |
| 发货单异常 | 撤销、截单、少收、异常终止后的库存与 ERP 回滚规则待定 |
| VMI 协同 | 供应商提报/审核/收货确认的责任边界待定 |
| ERP 接口 | 发货、收货、退货、物流轨迹能力与同步频率待联调 |
| 原型数据 | 全部为 mock，不代表真实业务量 |

## 九、术语速查

| 术语 | 含义 |
|---|---|
| 中台 | 位于业务系统与外部 ERP 之间，统一主数据、单据和库存口径 |
| 易仓 / 领星 | 外部 ERP；非亚马逊团队主要对接易仓，亚马逊团队主要对接领星 |
| 货权 | 库存归哪个团队/平台/店铺所有 |
| 组合品 / 子件 | 套装 SKU 及其 BOM 子 SKU；采购按子件，物流加工按套装 |
| 履约 | 提货、加工、发货、收货全过程 |
| 批次 | 每次提货/加工/发货/收货生成的可追溯记录 |
| 申报量 | 发货时申报的数量口径，区别于计划量和实发量 |

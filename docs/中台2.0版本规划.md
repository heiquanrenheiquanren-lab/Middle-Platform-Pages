# 中台 2.0 版本规划

## 一、基础数据

### 1.1 国家与站点管理

**业务目标**

通过维护国家基础数据统一全系统国家字段口径，避免同一国家多种写法导致的数据混乱；通过维护站点时区和夏令时/冬令时信息，确保促销、广告、截单、报表等时效性业务按正确的站点时区执行，避免因时区偏差导致运营失误。

**1.0 现状**

1. **缺少国家基础配置**：各页面需要使用国家字段时分别维护，口径不统一，容易出现同一国家多种写法。
2. **缺少站点管理**：各平台站点信息（如亚马逊美国站、日本站等）散落在不同模块，夏令时/冬令时切换时间没有统一维护，导致促销活动、广告排期、订单截单时间和数据报表按站点时区计算时出现偏差，影响运营决策和发货时效。

**2.0 规划**

1. **国家管理**：新增国家管理列表，维护中文名称、英文名称、国家编码、国家区域和国家图标，供其他模块下拉引用，统一全系统国家数据口径。
2. **站点管理**：新增站点管理列表，维护平台、站点名称、所属国家、冬令时开始时间、冬令时结束时间、冬令时差、夏令时开始时间、夏令时结束时间和夏令时差。
3. **统一引用和治理**：为促销、广告、订单截单、报表、库存、发货和运营分析提供准确的站点时区基准，并支持编码校验、启用/停用和变更记录。

### 1.2 产品主数据管理

**业务目标**

通过将 SKU 多维度资料整合到详情弹窗内，提升产品信息维护效率；通过建立产品线维度实现产品结构化分类，支持按产品线聚合统计销售、利润和库存数据；通过品牌维度支持品牌授权和合规场景；通过统一管理产品认证资质解决合规审核找不到资质的问题，并实现资质到期预警。

**1.0 现状**

1. **SKU 维护交互繁琐**：产品资料、采购资料、报关资料和运营资料被拆成多个标签页分别维护，用户需要在多个页面之间切换才能完成一个 SKU 的全部信息录入，操作路径长、效率低。
2. **缺少关键一级菜单**：产品线管理、品牌管理、资质管理等基础维度缺失，产品分类混乱，无法按产品线或品牌聚合统计销售和利润数据；FCC、CE、RoHS 等产品资质没有统一存档，合规审核时难以快速找到。

**2.0 规划**

1. **SKU 详情弹窗**：将基础资料、采购资料、报关资料和运营资料整合到 SKU 详情弹窗内，通过 Tab 分组切换，一个入口完成所有维度信息维护。
2. **产品线管理**：新增产品线一级菜单，支持创建、编辑和归档产品线；SKU 归属到产品线，并支持按产品线聚合统计。
3. **品牌管理**：新增品牌一级菜单，维护品牌名称、LOGO、所属国家等信息，支持 SKU 关联品牌。
4. **资质管理**：新增资质一级菜单，维护产品认证资质名称、编号、有效期和附件，支持 SKU 关联资质，并在资质到期前预警。

### 1.3 捆绑销售管理

**业务目标**

通过建立虚拟捆绑 SKU（套装 SKU）概念，解决同一套装在多平台分散映射不同 SellerSKU 导致销量无法聚合统计的问题，为备货计划和采购计划提供准确的套装维度销量数据。

**1.0 现状**

1. **无虚拟捆绑 SKU 概念**：当前中台只有实物 SKU，没有套装/捆绑 SKU 的定义，无法表达“焊机 + 焊帽 + 焊条”这类组合套装的产品关系。
2. **套装销量分散统计**：同一个套装在不同平台映射了不同的 SellerSKU，例如 SellerSKU A、SellerSKU B、SellerSKU C，三个平台分别统计销量，运营无法直接看到该套装全平台总销量，需要手动汇总后再做备货和采购，效率低且容易出错。

**2.0 规划**

1. **新增捆绑 SKU 管理**：创建虚拟捆绑 SKU，定义套装包含的实物 SKU 及各自数量。
2. **多平台 SellerSKU 映射**：将同一捆绑 SKU 与多个平台的 SellerSKU 建立映射关系，实现跨平台套装归属。
3. **套装销量聚合**：订单销售数据按捆绑 SKU 维度自动聚合，直接展示某套装全平台总销量，为备货计划和采购计划提供数据支撑。

### 1.4 海外仓 SKU 映射

**业务目标**

通过将海外仓 SKU 与 FNSKU 映射能力从仓库管理迁移到产品管理模块，简化维护流程；同时补齐 FNSKU 映射，支撑发货预报自动引用编码和海外仓库存精确管理。

**1.0 现状**

1. **海外仓 SKU 维护入口错位**：当前海外仓 SKU 维护功能放在“仓库管理”模块下，但海外仓 SKU 本质上是产品编码的延伸映射，维护时需要对照产品信息，放在仓库管理导致路径深、操作繁琐。
2. **缺少 FNSKU 映射**：第三方海外仓 SKU 编码有维护入口，但亚马逊 FBA 专用的 FNSKU 映射完全缺失。发 FBA 单时运营需要临时去卖家后台查找并手动填入，库存管理也无法精确到 FNSKU 维度，容易出现本地 SKU 库存正确但 FNSKU 维度不一致的问题。
3. **操作流程复杂**：现有海外仓 SKU 维护步骤繁琐，添加一个 SKU 的海外仓编码需要多次页面跳转，批量维护时效率低。

**2.0 规划**

1. **入口迁移**：将海外仓 SKU 维护从“仓库管理”迁移到“产品管理”，与本地 SKU 信息合并展示，缩短维护路径。
2. **补齐 FNSKU 映射**：在产品管理模块新增 FNSKU 映射入口，支持按亚马逊站点维护本地 SKU 与 FNSKU 的对应关系。
3. **简化操作流程**：在 SKU 详情弹窗内直接维护海外仓 SKU 和 FNSKU 映射，一个入口完成所有编码维护。
4. **发货预报自动引用**：发货单入库预报时，根据目标海外仓和站点自动带出映射后的海外仓 SKU/FNSKU，无需手动查填。
5. **库存对账校验**：海外仓库存同步时按映射关系自动匹配本地 SKU，支持按海外仓 SKU/FNSKU 维度精确查询库存。

## 二、全局用户体验优化

### 2.1 视觉规范与组件库

**业务目标**

通过统一设计规范和业务组件库，降低开发和维护成本，消除多套标准并存导致的重复造轮子和样式不一致问题，新页面开发效率可提升 50% 以上。

**1.0 现状**

1. 3 套主色混用（#1890ff / #1677ff / #1683e8），字号、圆角、间距无统一规范，各页面视觉风格不一致。
2. 部分页面加载未使用的 `element-plus.css`，同时在 `global-export.css` 中重复封装了多个 Element Plus 组件，增加加载体积和维护成本。
3. 自定义组件和 Element Plus 组件的 hover 色、弹窗关闭、分页和按钮样式不一致，页面交互体验割裂。

**2.0 规划**

1. 定义 Design Token，统一色板、字号、间距、圆角和阴影。
2. 封装 `BaseDialog`、`BaseTable`、`BaseFilter`、`BasePagination` 等业务组件，统一使用 Element Plus。
3. 清理冗余 CSS 和重复组件，统一行内编辑、Toast、空状态、加载态和响应式交互。

### 2.2 用户账号与飞书对接

**业务目标**

通过建立独立账号体系解决操作者身份无法区分、操作记录不可追溯的问题；通过对接飞书通讯录实现账号自动同步，降低账号维护成本，避免离职人员未禁用导致的安全隐患。

**1.0 现状**

1. **无账号体系**：当前中台没有独立的用户登录系统，无法区分操作者身份，所有操作记录无法追溯到具体人员。
2. **未对接飞书通讯录**：公司已使用飞书办公，但中台没有和飞书组织通讯录打通，用户无法通过飞书扫码或手机号直接登录，需要额外维护一套账号密码。

**2.0 规划**

1. **登录对接飞书通讯录**：同一飞书组织下的成员支持通过飞书扫码或飞书绑定的手机号直接登录中台，无需额外注册账号。
2. **账号与飞书组织自动同步**：同步组织、部门和人员状态，离职人员自动禁用，无需手动维护账号生命周期。
3. **操作身份统一**：所有新增、修改、删除、审核、导出等操作绑定到具体用户，支持按用户追溯操作记录。

### 2.3 权限与数据隔离

**业务目标**

通过建立店铺级数据隔离满足“运营只看自己负责的店铺单据”的基本业务需求，降低数据泄露风险；通过敏感字段权限机制满足合规要求，确保供应商价格、联系方式等敏感信息仅对授权角色可见。

**1.0 现状**

1. **无店铺权限管控**：当前所有账号看到的数据范围完全一致，没有店铺级别的数据隔离，无法满足“某运营只看自己负责的店铺单据”等基本权限需求，存在数据泄露风险。
2. **无敏感字段管控**：供应商名称、供应商地址、联系方式、采购价格等敏感字段未做权限控制，所有有账号的人都能看到，无法满足“某些字段仅特定角色可见”的合规要求。

**2.0 规划**

1. **店铺权限管理**：管理员可按账号配置店铺访问权限，未授权的店铺单据、订单、库存等数据对无权限账号不可见，实现店铺级数据隔离。
2. **敏感字段权限**：维护敏感字段清单，例如供应商名称、地址、联系方式、采购价格等，再按角色或账号分配字段可见权限；未授权字段在页面中脱敏或隐藏。
3. **权限模型落地**：权限同时覆盖菜单、按钮、接口、数据范围、字段和导出权限，支持按部门、岗位、团队、平台、店铺、仓库及国家/站点进行授权。
4. **审计留痕**：记录权限变更、敏感字段查看、数据导出和高风险业务操作，满足问题追溯和合规审计要求。

### 2.4 账号安全与登录会话管理

**业务目标**

在独立账号基础上，加强登录安全和会话管理，确保账号使用人可识别、风险可控制、权限可及时回收。

**1.0 现状**

多人共用账号会导致：

1. 无法确认具体是谁执行了删除、导出、修改等操作，审计不可追责。
2. 一台电脑泄露密码后，其他人的权限会被连带暴露。
3. 员工离职、转岗时无法只撤销个人权限。

**2.0 规划**

1. 每位员工使用独立账号，支持查看登录设备和会话状态。
2. 支持用户退出其他设备，以及管理员强制下线高风险会话。
3. 记录用户、设备、会话和操作之间的关联关系，支持异常登录和高风险操作追溯。

## 三、供应链中台

### 3.1 库存管理

**业务目标**

通过分离库存领域与销售领域，从根本上解决货权与销售归属混淆导致的超卖风险、数据爆炸和维护成本问题；通过规范库存类型消除跨团队语义歧义；通过整合页面减少操作路径；通过补齐流水实现库存变动可追溯。

**系统能力**

1. 建立按 SKU、仓库、团队和批次管理的库存账本，统一库存类型和可用量计算规则。
2. 支持入库、出库、调拨、盘点、调整和接口同步等库存流水追溯。
3. 提供库存对账、库存冻结、库存预警和异常处理能力。

**1.0 现状**

1. **货权与销售归属混淆**：当前库存粒度包含 SKU + 仓库 + 团队 + 平台 + 店铺 + SellerSKU，把“库存领域”（SKU、仓库、团队、批次、库龄）和“销售领域”（平台、店铺、SellerSKU、Listing）强行拼成一条库存记录。新品采购时 SellerSKU 可能尚未创建，导致无法入库；同一批 100 件货若被 2 个店铺共享，会被拆成 2 条记录，容易出现重复统计或人为切分；SellerSKU 随平台和站点频繁变动，库存主数据跟着震荡，维护成本高；库龄也会被拆碎并复制到多条记录，冗余且容易出错。
2. **库存类型不规范**：当前使用“在库量”“在库（待发）量”“在途/在产量”等自定义口径，缺乏行业标准语义，后续容易衍生出“待退量”“待补量”等非标准类型，库存状态边界模糊，跨团队沟通成本高。
3. **库存页面过多且冗余**：当前库存相关页面多达 7 个，包括供应商库存、平台仓&海外仓库存、入库批次查询、库存总览、分仓明细、团队库存总览、团队库存分仓明细。用户需要在多个页面之间频繁跳转，操作路径长，数据视角分散。
4. **缺少库存流水**：库存变动无记录可查，无法追溯某批货每一次出入库变动，出现问题时难以定位原因。

**2.0 规划**

1. **库存维度收敛**：仅保留 SKU + 仓库 + 团队（货主）作为库存核心维度，库存记录对应物理实物，不再按店铺或 SellerSKU 拆分。
2. **销售属性剥离**：平台、店铺、SellerSKU 从库存主表剥离，仅作为出库扣减时的引用信息，与库存记录解耦。
3. **订单扣减规则**：按“渠道货 → 团队通用货 → 公共库存”的顺序自动路由，在单事务内完成扣减，并配合并发锁防止超卖。
4. **库存类型规范化**：统一为“可用库存、在途库存、占用库存、待确认库存”，明确每种类型的语义边界和流转规则。
5. **库存页面整合**：将 7 个页面合并为“库存总览、库存明细、库存流水”3 个核心视图，减少页面跳转。
6. **补齐库存流水**：支持按 SKU、仓库和时间范围查询每一次库存变动明细，实现库存数据可追溯。

### 3.2 备货计划、采购计划与发货计划

**业务目标**

建立从需求识别、供需平衡到采购和发货执行的计划协同机制，避免计划单相互重复生成或互相覆盖。

**系统能力**

1. 建立备货计划、采购计划和发货计划的主单、明细及供需匹配关系。
2. 支持区分海外/国内备货，并计算需求、库存、在途、安全库存和采购交期。
3. 支持多 SKU 计划单、数量校验、执行进度和跨单据关联，避免重复生成和超量执行。

**1.0 现状**

备货计划、采购计划和发货计划的边界及关联关系不够清晰，计划单以单个 SKU 为单位拆分，难以完整表达同一批次、同一目的仓或同一供应需求。

**2.0 规划**

1. 备货计划创建时区分海外备货和国内备货，并增加目标团队、目的仓、需求时间和供应来源等信息。
2. 备货计划作为供需平衡计划，综合考虑需求、现有库存、在途库存、已安排发货量、安全库存和采购交期。
3. 采购计划用于承接备货计划中的供应缺口，记录需要采购的 SKU、数量、预计到货时间、供应商和采购策略。
4. 发货计划用于安排可用库存向目的仓发运，不与采购计划形成简单的上下游父子关系。
5. 采购计划、发货计划可以来源于备货需求，但三者通过需求明细、SKU、数量、仓库和批次建立供需匹配关系。
6. 支持一个计划单包含多个 SKU 和多条明细，避免“一张 SKU 一张计划单”导致单据数量膨胀、需求被拆散、审批和统计效率下降。
7. 计划单保留计划数量、已生成数量、已执行数量、已完成数量和剩余数量，防止重复创建和超量执行。

### 3.3 采购单主系统与多 ERP 执行协同

**业务目标**

将采购单完整沉淀在中台，避免易仓、领星和中台分别维护采购单造成数量、成本、入库、库存金额、供应商及付款状态不一致，保证采购、库存、财务和审计数据形成唯一、完整、可追溯的业务链路。

**系统能力**

1. 统一管理采购数量、价格、成本、供应商、交期、入库、返利、付款和账期。
2. 支持同 SKU 比价、采购成本跟踪、SKU 到仓成本和三层毛利成本池核算。
3. 支持采购计划、采购单、入库、发票和付款之间的关联。
4. 支持易仓、领星执行任务同步、结果回传、异常处理和对账，确保采购主单只能在中台维护。

**1.0 现状**

1. 当前采购单统一推送至易仓，易仓收货入库后，属于亚马逊的货物需要再做其他出库，扣减易仓库存。
2. 领星侧再通过其他入库增加亚马逊货物库存，采购业务因此分散在中台、易仓和领星多个系统中。
3. 如果中台、易仓和领星的采购单都可以独立修改，会形成三套采购数量、三套采购成本、三套入库数量、三套库存金额、三套供应商和付款状态。
4. 财务无法准确判断哪一张是真实采购单，发票、合同、付款和入库记录也无法准确对应，后续请款、成本核算、库存核算和审计追溯都存在风险。

**2.0 规划**

1. 采购单统一在中台创建、审核、修改和关闭，中台采购单作为采购业务唯一主单。
2. 易仓、领星不再独立维护采购业务主单，仅根据中台采购单生成执行任务或执行副本，并回传收货、质检和入库结果。
3. 易仓和领星的执行记录必须关联中台采购单号、采购单明细号和外部执行单号，禁止外部系统独立修改供应商、采购数量、采购价格、税率等核心字段。
4. 中台统一沉淀采购数量、采购成本、入库数量、库存金额、供应商、发票、付款和采购状态，避免同一采购业务在多个系统重复维护。
5. 建立中台与易仓、领星之间的同步状态、回传结果、异常处理和对账机制，替代通过其他出库/其他入库进行人工库存倒转。
6. 采购计划与采购单采用一对多关系，采购计划支持“待采购、采购中、部分到货、已完成、已关闭”等状态，并按采购单入库结果自动更新。

**核心原则**

中台采购单是唯一业务主单；易仓和领星是执行系统，不是第二套采购主系统。三套系统可以存在执行记录，但不应存在三张可以独立修改、独立作为财务依据的采购主单。

### 3.4 供应链经营指标与预警

**业务目标**

把供应链数据从事后统计推进到过程管理，为采购、库存和供应商决策提供统一指标。

**2.0 规划**

1. 建立 30/60/90 天预测准确率、库存周转、采购成本、供应商交付及时率、加权账期等指标。
2. 建立未来 13 周滚动预测，支持按团队、仓库、平台、店铺、SKU 和供应商查看。
3. 对库存库龄、缺货风险、采购延期、采购成本异常和供应商履约异常进行预警。
4. 支持按周/月输出库存健康度、供应链执行率和采购降本结果。

### 3.5 亚马逊 FBA 发货单管理

**业务目标**

支持亚马逊 FBA 货件在中台形成对应发货单，统一管理发货仓、供应商仓、海外仓在途及最终接收情况，确保 FBA 发货过程可追踪、库存可核对。

**1.0 现状**

当前发货单不支持亚马逊 FBA 货件。运营虽然会先在亚马逊店铺创建 FBA 货件，但中台没有对应发货单，无法统一管理发货仓出库、供应商仓待发、海外仓在途和最终接收数量，FBA 货件也无法与采购、入库和库存数据完整关联。

**2.0 规划**

1. 支持将亚马逊店铺创建的 FBA 货件同步或录入为中台发货单，关联店铺、站点、FBA 货件、SKU/FNSKU、数量和目的仓。
2. 支持管理发货仓、供应商仓、海外仓在途和 FBA 接收等关键环节。
3. 发货单关联发货计划、采购单、入库批次和库存流水，记录出库数量、在途数量和最终接收数量。
4. 支持部分发货、部分接收、短收等异常情况。

### 3.6 采购对账与物流对账

**业务目标**

建立统一的采购对账和物流对账机制，将采购单、入库单、物流单、费用账单和请款单进行关联，先完成业务对账，再进入财务请款，避免直接请款导致数据不准确、流程不可回退和财务无法追溯。

**系统能力**

1. 建立采购对账单、物流对账单的独立单据模型，记录对账明细、金额、差异、关联单据和处理状态。
2. 支持采购单与入库数量、采购金额、退货数量的核对，以及物流单与物流账单、计费重量、物流费用的核对。
3. 支持对账单提交、审核、退回、重新对账和确认完成，退回时记录原因。
4. 对账确认后生成对应请款单，请款单关联对账单和原始业务单据。

**1.0 现状**

1. **物流对账未上线**：物流费用涉及物流单、计费重量、运输方式和供应商账单等多个因素，现有逻辑复杂，用户不容易理解，页面操作繁琐，主流程也不够合理。
2. **采购对账未上线**：现有采购对账功能较为简单，没有独立的采购对账单，也不支持退回或回退操作，采购单完成后直接进入请款，缺少规范的业务核对环节。
3. 请款单与采购单、入库单、物流单等原始业务数据关联不完整，出现差异时难以定位和追溯。

**2.0 规划**

1. 新增采购对账单和物流对账单，作为采购、物流和请款之间的中间业务单据。
2. **采购对账**：根据采购单、入库单和退货数据核对采购数量及金额，对账确认后再生成请款单。
3. **物流对账**：根据发货单、物流单和物流账单核对物流费用，简化对账操作，明确费用来源和差异处理方式。
4. 对账单支持草稿、待审核、已退回、对账完成和已关闭等状态，并支持退回后重新提交。
5. 请款单必须由已确认的采购对账单或物流对账单生成，并保留与原始单据的完整关联关系。

### 3.7 辅料包材管理与库存货权调整

**业务目标**

完善辅料包材和库存货权管理能力，支持辅料包材作为 SKU 进行维护、消耗和成本核算；同时将平台仓、海外仓的货权调整规范为独立单据，确保库存数量、货权归属和成本变动可追溯。

**系统能力**

1. 支持维护辅料包材 SKU、消耗数量、配比和单价，并自动计算辅料包材成本。
2. 支持记录辅料包材的实际消耗数量和消耗成本，按 SKU 进行统计。
3. 建立货权调整单，记录调整 SKU、仓库、来源团队、调入团队、调整数量、调整原因和处理状态。
4. 货权调整单完成后同步更新库存归属，并生成对应的库存流水。

**1.0 现状**

1. 当前未完整支持辅料包材 SKU、数量配比、单价及成本核算，库内加工时无法准确记录辅料包材的消耗数量和成本。
2. 当前平台仓、海外仓的货权调整缺少独立单据，调整过程和库存归属变更缺少规范记录，无法完整追溯。

**2.0 规划**

1. 新增辅料包材 SKU 管理，维护辅料包材与产品之间的数量配比、单价和成本。
2. 库内加工或相关业务发生辅料包材消耗时，自动扣减对应库存，并记录消耗数量和成本。
3. 新增库存货权调整单，支持平台仓、海外仓在不同团队之间进行货权调整。
4. 货权调整单支持草稿、提交、完成和作废等状态，完成后同步更新库存归属并记录库存流水。

## 四、运营中台

### 4.1 订单结算状态、结算账单与费用账单对接

**业务目标**

通过订单和 SKU 关联账单获取结算、费用数据，再按照分摊规则分摊至 SKU 维度，实现单 SKU 利润核算。

**系统能力**

1. 统一结算、物流、广告和费用账单的数据模型与字段口径，支持 RPA 或接口接入。
2. 支持账单清洗、订单/SKU 匹配、费用分摊和异常处理。
3. 支持 SKU 净利润计算、利润台账、数据重算和审计追溯。

**功能范围**

新增账单管理模块，支持按平台、订单、SKU、账期和账单类型维护映射关系及分摊逻辑，并为订单结算状态标记、费用归集和利润核算提供统一数据基础。

**1.0 现状**

账单数据散落在各个平台，结算账单、物流账单和广告账单的字段及口径不统一，财务依赖人工下载、清洗和核算，无法稳定做到单 SKU 利润核算。

**2.0 规划**

1. 将各平台结算账单、物流账单和广告账单统一为标准字段格式，统一数据指标口径，包括数据来源、指标名称、指标定义和计算公式。
2. 通过 RPA 自动登录各平台下载账单，按照统一数据模板进行清洗加工，并将结算账单和费用账单关联到具体订单和 SKU。
3. 建立订单结算状态标记能力，区分未结算、部分结算、已结算和异常等状态，支持按订单和 SKU 查询结算进度。
4. 按照既定分摊规则自动计算每个 SKU 的净利润，并支持分摊结果查看、异常修正和重新计算。
5. 搭建利润台账，按日、周、月自动更新，支持按 SKU、平台、店铺和国家等多维度下钻。
6. 建立订单、SKU、结算账单、费用账单、采购成本和库存成本之间的关联关系，为财务核算、请款和经营分析提供统一数据基础。

### 4.2 运营分析看板

**业务目标**

构建贯穿“订单、用户、流量、库存、产品”五大维度的全链路经营监控体系，打破跨平台数据孤岛，实现从宏观销售趋势到微观业务异常（如缺货预警、单品利润下滑、流量波动）的实时穿透与精准洞察，为管理层及运营团队提供一站式的数据决策视图。

**系统能力**

1. 建立跨平台订单、用户、流量、库存和产品的统一分析模型及指标口径。
2. 支持驾驶舱、趋势分析、平台/区域对比和多层级下钻。
3. 支持用户价值分层、异常预警、数据权限和从指标定位到业务明细。

**功能范围**

提供经营健康度总览及核心指标（销售额、利润、订单量）的日/周/月趋势分析；支持按平台、站点、省州等维度拆解销售结构，对比多平台经营明细；分析新老客户占比及价值差异，辅助复购策略制定。

**1.0 现状**

1. 数据孤岛：各平台数据分散，缺乏统一视图，无法跨平台对比经营效果。
2. 监控滞后：缺乏实时预警机制，缺货等异常情况发现滞后，影响销售。
3. 分析浅层：仅有基础销售报表，缺乏对用户价值、地域分布及库存周转的深度关联分析。

**2.0 规划**

1. **搭建全局经营驾驶舱**：全面打通并整合多平台底层数据，上线“全局经营健康度看板”与 GMV、订单量、转化率等核心指标趋势图，实现一屏统揽大盘，让管理层 5 分钟内快速掌握业务整体健康状态。
2. **深化多维交叉分析**：新增平台销售结构饼图、站点/省州地理热力图及多平台经营对比表，支持从宏观大盘下钻至微观区域与渠道，精准定位高潜市场与异常波动节点，为资源倾斜与精细化运营提供数据支撑。
3. **完善用户价值画像**：上线新老客分析模型，深度挖掘客户行为轨迹与生命周期价值（LTV），输出客户价值分层报表，辅助运营团队制定差异化拉新与复购策略，提升整体客单与留存率。
4. **建立异常穿透能力**：将订单、库存、利润、缺货和流量等异常指标与预警机制关联，支持从看板直接定位到平台、店铺、国家/站点、SKU 或订单明细。

# 供应链中台 2.0 版本规划

> 业务目标：降本增效。产品目标：深化现有链路，把 1.0 已铺开但还没闭合的断点补成闭环。

| 序号 | 业务模块 | 子项 | 业务目标 | 功能说明 | 1.0 现状 | 2.0 要做什么 | 优先级 |
|:---:|---|---|---|---|---|---|---|
| 1 | UI 改造 | 视觉规范、组件库 | 通过统一设计规范和业务组件库，降低开发和维护成本，消除多套标准并存导致的重复造轮子和样式不一致问题，新页面开发效率可提升 50% 以上 | 统一视觉风格、交互规范，消除多套标准和重复造轮子 | 1. 3 套主色混用（#1890ff / #1677ff / #1683e8），字号、圆角、间距无统一规范，各页面视觉风格不一致；<br/>2. 4 个页面（采购单、备货计划、采购计划、供应商库存）加载了 element-plus.css 但 HTML 中实际未使用任何 Element Plus 组件，白白增加首屏加载体积；<br/>3. global-export.css 里封装了 7 个与 Element Plus 功能重复的自定义组件（.gx-dialog / .gx-table / .gx-btn / .gx-filter / .gx-pagination / .gx-toast / .gx-multi-select），重复造轮子且交互不一致；<br/>4. 自定义组件和 Element Plus 组件的交互行为不统一，例如 hover 色、弹窗关闭策略、分页位置和按钮样式各页面写法不同，用户在不同页面之间切换时有割裂感。 | 1. 定 Design Token 统一色板 / 字号 / 间距 / 圆角 / 阴影，全系统只出一种蓝；<br/>2. 封装 BaseDialog / BaseTable / BaseFilter / BasePagination 等业务组件库，底层统一走 Element Plus；<br/>3. 清理冗余 CSS 和重复造轮子代码，移除未使用的 element-plus.css 引用；<br/>4. 交互细节（行内编辑、Toast 通知、空状态、加载态、响应式断点）统一走组件库，不再各页面自实现。 | P0 |
| 2 | 库存管理 | 模型重构、类型规范、页面整合、流水补齐 | 通过分离库存领域与销售领域，从根本上解决货权与销售归属混淆导致的超卖风险、数据爆炸和维护成本问题；通过规范库存类型消除跨团队语义歧义；通过整合页面减少操作路径；通过补齐流水实现变动可追溯 | 分离库存领域与销售领域，重塑库存底层模型，规范库存类型，整合页面并补齐流水能力 | 1. 货权与销售归属混淆：当前库存粒度包含了 SKU + 仓库 + 团队 + 平台 + 店铺 + SellerSKU，把"库存领域"（SKU/仓库/团队/批次/库龄）和"销售领域"（平台/店铺/SellerSKU/Listing）强行拼成一条库存记录，导致：新品采购时 SellerSKU 可能尚未创建，无法入库；同一批 100 件货若被 2 个店铺共享，按此粒度会拆成 2 条记录，容易出现重复统计或人为切分，盘点对账困难；SellerSKU 随平台 / 站点频繁变动，库存主数据跟着震荡，维护成本极高；库龄被拆碎，同一批货的入库时间被复制到多条记录，冗余且易出错；<br/>2. 库存类型不规范：当前使用"在库量""在库（待发）量""在途/在产量"等自定义口径，缺乏行业标准语义，后续容易衍生出"待退量""待补量"等非标类型，库存状态的语义边界模糊，跨团队沟通成本高；<br/>3. 库存页面过多且冗余：当前和库存相关的页面多达 7 个（供应商库存、平台仓&海外仓库存、入库批次查询、库存总览、分仓明细、团队库存总览、团队库存分仓明细），用户在不同页面之间频繁跳转，操作路径长，数据视角分散；<br/>4. 缺少库存流水：库存变动无记录可查，用户无法追溯某批货的每一次出入库变动，出问题时难以定位原因。 | 1. 库存维度收敛：仅保留"SKU + 仓库 + 团队（货主）"作为库存核心维度，库存记录对应物理实物，不再按店铺/SellerSKU 拆分；<br/>2. 销售属性剥离：平台 / 店铺 / SellerSKU 从库存主表剥离，仅作为出库扣减时的引用信息，与库存记录解耦；<br/>3. 订单扣减规则：按"渠道货 → 团队通用货 → 公共库存"优先级自动路由，单事务内完成扣减，配合并发锁防超卖；<br/>4. 库存类型规范化：统一为行业标准"可用库存、在途库存、占用库存、待确认库存"，明确每种类型的语义边界和流转规则；<br/>5. 库存页面整合：将 7 个页面合并为"库存总览、库存明细、库存流水"3 个核心视图，减少页面跳转；<br/>6. 补齐库存流水：按 SKU / 仓库 / 时间范围查询每一次库存变动明细，实现数据可追溯。 | P0 |
| 3 | 用户管理 | 账号体系、飞书对接 | 通过建立独立账号体系解决操作者身份无法区分、操作记录不可追溯的问题；通过对接飞书通讯录实现账号自动同步，降低账号维护成本，避免离职人员未禁用导致的安全隐患 | 完善用户账号体系，对接飞书通讯录，建立统一的登录入口 | 1. 无账号体系：当前中台没有独立的用户登录系统，无法区分操作者身份，所有操作记录无法追溯到具体人员；<br/>2. 未对接飞书通讯录：公司已使用飞书办公，但中台没有和飞书组织通讯录打通，用户无法通过飞书扫码或手机号直接登录，需要额外维护一套账号密码。 | 1. 登录对接飞书通讯录：同一飞书组织下的成员，支持通过飞书扫码或飞书绑定的手机号直接登录中台，无需额外注册账号；<br/>2. 账号与飞书组织自动同步，离职人员自动禁用，无需手动维护账号生命周期。 | P0 |
| 4 | 权限管理 | 店铺权限、敏感字段 | 通过建立店铺级数据隔离满足"运营只看自己负责的店铺单据"的基本业务需求，降低数据泄露风险；通过敏感字段权限机制满足合规要求，确保供应商价格、联系方式等敏感信息仅对授权角色可见 | 建立店铺级数据隔离和敏感字段管控，按角色/账号分配可见范围 | 1. 无店铺权限管控：当前所有账号看到的数据范围完全一致，没有任何店铺级别的数据隔离，无法满足"某运营只看自己负责的店铺单据"这类基本权限需求，存在数据泄露风险；<br/>2. 无敏感字段管控：供应商名称、供应商地址、联系方式、采购价格等敏感字段未做权限控制，所有有账号的人都能看到，无法满足"某些字段仅特定角色可见"的合规需求。 | 1. 店铺权限管理：管理员可按账号配置店铺访问权限，未授权的店铺单据、订单、库存等数据对无权限账号不可见，实现店铺级数据隔离；<br/>2. 敏感字段权限：先维护敏感字段清单（如供应商名称、地址、联系方式、采购价格等），再按角色/账号分配字段可见权限，未授权字段在页面中脱敏或隐藏，满足合规要求。 | P0 |
| 5 | 基础配置 | 国家管理、站点管理 | 通过维护国家基础数据统一全系统国家字段口径，避免同一国家多种写法导致的数据混乱；通过维护站点时区和夏令时/冬令时信息，确保促销、广告、截单、报表等时效性业务按正确的站点时区执行，避免因时区偏差导致的运营失误 | 维护国家、站点等基础数据字典，为其他业务模块提供统一的数据引用 | 1. 没有国家基础配置，各页面需要用国家字段时各写各的，口径不统一，容易出现同一国家多种写法；<br/>2. 没有站点管理，各平台的站点信息（如亚马逊美国站、日本站等）散落在不同模块，夏令时/冬令时切换时间没有统一维护，导致促销活动、广告排期、订单截单时间、数据报表等按站点时区计算时出现偏差，影响运营决策和发货时效。 | 1. 国家管理：新增国家管理列表，维护中文名称、英文名称、国家编码、国家区域、国家图标，供其他模块下拉引用，统一全系统国家数据口径；<br/>2. 站点管理：新增站点管理列表，维护平台、站点名称、所属国家、冬令时（开始时间、结束时间、时差）、夏令时（开始时间、结束时间、时差），为促销、广告、订单截单、报表等时效性业务提供准确的站点时区基准。 | P1 |
| 6 | 产品管理 | SKU 维护交互、产品线管理、品牌管理、资质管理 | 通过将 SKU 多维度资料整合到详情弹窗内，提升产品信息维护效率；通过建立产品线维度实现产品结构化分类，支持按产品线聚合统计销售、利润、库存数据；通过品牌维度支持品牌授权和合规场景；通过统一管理产品认证资质解决合规审核找不到资质的问题，并实现到期预警 | 重构 SKU 维护交互，补齐产品线、品牌、资质等一级菜单，完善产品主数据管理 | 1. SKU 维护交互繁琐：产品资料、采购资料、报关资料、运营资料被拆成多个标签页分别维护，用户需要在多个页面之间切换才能完成一个 SKU 的全部信息录入，操作路径长、效率低；<br/>2. 缺少关键一级菜单：产品线管理、品牌管理、资质管理等基础维度缺失，产品分类混乱，无法按产品线或品牌聚合统计销售和利润数据，产品资质（如 FCC、CE、RoHS 等）没有统一存档，合规审核时找不到。 | 1. SKU 详情弹窗：将基础资料、采购资料、报关资料、运营资料整合到 SKU 详情弹窗内，通过 Tab 分组切换，一个入口完成所有维度信息维护；<br/>2. 产品线管理：新增产品线一级菜单，支持创建/编辑/归档产品线，SKU 归属到产品线，支持按产品线聚合统计；<br/>3. 品牌管理：新增品牌一级菜单，维护品牌名称、LOGO、所属国家等信息，SKU 关联品牌；<br/>4. 资质管理：新增资质一级菜单，维护产品认证资质（名称、编号、有效期、附件），支持 SKU 关联资质，资质到期前预警。 | P0 |
| 7 | 产品管理 | 捆绑销售 | 通过建立虚拟捆绑 SKU（套装 SKU）概念，解决同一套装在多平台分散映射不同 SellerSKU 导致的销量无法聚合统计的问题，为备货计划和采购计划提供准确的套装维度销量数据 | 新增虚拟捆绑 SKU 管理，支持多平台 SellerSKU 映射，实现套装销量聚合统计 | 1. 无虚拟捆绑 SKU 概念：当前中台只有实物 SKU，没有套装 / 捆绑 SKU 的定义，无法表达"焊机 + 焊帽 + 焊条"这类组合套装的产品关系；<br/>2. 套装销量分散统计：同一个套装在不同平台映射了不同的 SellerSKU（如 SellerSKUA、SellerSKUB、SellerSKUC），三个平台各自统计销量，数据分散成三笔，运营无法直接看到这个套装总共卖了多少件，需要手动汇总再做备货和采购，效率低且容易出错。 | 1. 新增捆绑 SKU 管理：创建虚拟捆绑 SKU，定义套装包含的实物 SKU 及各自数量；<br/>2. 多平台 SellerSKU 映射：将同一捆绑 SKU 与多个平台的 SellerSKU 建立映射关系，实现跨平台套装归属；<br/>3. 套装销量聚合：订单销售数据按捆绑 SKU 维度自动聚合，直接展示某套装全平台总销量，为备货计划和采购计划提供数据支撑。 | P0 |
| 8 | 产品管理 | 海外仓 SKU 映射 | 通过将海外仓 SKU 与 FNSKU 映射能力从仓库管理迁移到产品管理模块，简化维护流程；同时补齐 FNSKU 映射缺失，支撑发货预报自动引用编码和海外仓库存精确管理 | 迁移海外仓 SKU 维护到产品管理模块，补齐 FNSKU 映射，简化操作并支撑发货与库存精确管理 | 1. 海外仓 SKU 维护入口错位：当前海外仓 SKU 的维护功能放在"仓库管理"模块下，但海外仓 SKU 本质上是产品编码的延伸映射，维护时需要对照产品信息，放在仓库管理导致路径深、操作繁琐、维护效率低；<br/>2. 缺少 FNSKU 映射：第三方海外仓的 SKU 编码有维护入口，但亚马逊 FBA 专用的 FNSKU 映射完全缺失，发 FBA 单时运营需要临时去卖家后台查 FNSKU 手动填入，库存管理也无法精确到 FNSKU 维度，容易出现"本地 SKU 库存对了但 FNSKU 维度对不上"的问题；<br/>3. 操作流程复杂：现有海外仓 SKU 维护功能操作步骤繁琐，添加一个 SKU 的海外仓编码需要多次页面跳转，批量维护时效率极低。 | 1. 入口迁移：将海外仓 SKU 维护功能从"仓库管理"迁移到"产品管理"模块，与本地 SKU 信息合并展示，维护路径更短；<br/>2. 补齐 FNSKU 映射：产品管理模块内新增 FNSKU 映射维护入口，支持按亚马逊站点区分本地 SKU ↔ FNSKU 的对应关系；<br/>3. 简化操作流程：在 SKU 详情弹窗内直接维护海外仓 SKU 和 FNSKU 映射，一个入口完成所有编码映射；<br/>4. 发货预报自动引用：发货单入库预报时，根据目标海外仓 / 站点自动带出映射后的海外仓 SKU / FNSKU，无需手动查填；<br/>5. 库存对账校验：海外仓库存同步时按映射关系自动匹配本地 SKU，支持按海外仓 SKU / FNSKU 维度精确查询库存。 | P0 |

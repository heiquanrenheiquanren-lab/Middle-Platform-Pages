# 中台 2.0 版本规划

## 一、基础数据

### 1.1 国家与站点管理

**业务目标**

通过维护国家基础数据统一全系统国家字段口径，避免同一国家多种写法导致的数据混乱；通过维护站点时区和夏令时/冬令时信息，确保促销、广告、截单、报表等时效性业务按正确的站点时区执行，避免因时区偏差导致运营失误。

**1.0 现状**

1. **缺少国家基础配置**：各页面需要使用国家字段时分别维护，口径不统一，容易出现同一国家多种写法。
2. **缺少站点管理**：各平台站点信息（如亚马逊美国站、日本站等）散落在不同模块，夏令时/冬令时切换时间没有统一维护，导致促销活动、广告排期、订单截单时间和数据报表按站点时区计算时出现偏差，影响运营决策和发货时效。

**2.0 规划**

1. **国家管理**：新增国家管理列表，维护中文名称、英文名称、国家编码、国家区域和国家图标，供其他模块下拉引用，统一全系统国家数据口径。
2. **站点管理**：新增站点管理列表，维护平台、站点名称、所属国家、冬令时开始时间、冬令时结束时间、冬令时差、夏令时开始时间、夏令时结束时间和夏令时差。
3. **统一引用和治理**：为促销、广告、订单截单、报表、库存、发货和运营分析提供准确的站点时区基准，并支持编码校验、启用/停用和变更记录。

### 1.2 产品主数据管理

**业务目标**

通过将 SKU 多维度资料整合到详情弹窗内，提升产品信息维护效率；通过建立产品线维度实现产品结构化分类，支持按产品线聚合统计销售、利润和库存数据；通过品牌维度支持品牌授权和合规场景；通过统一管理产品认证资质解决合规审核找不到资质的问题，并实现资质到期预警。

**1.0 现状**

1. **SKU 维护交互繁琐**：产品资料、采购资料、报关资料和运营资料被拆成多个标签页分别维护，用户需要在多个页面之间切换才能完成一个 SKU 的全部信息录入，操作路径长、效率低。
2. **缺少关键一级菜单**：产品线管理、品牌管理、资质管理等基础维度缺失，产品分类混乱，无法按产品线或品牌聚合统计销售和利润数据；FCC、CE、RoHS 等产品资质没有统一存档，合规审核时难以快速找到。

**2.0 规划**

1. **SKU 详情弹窗**：将基础资料、采购资料、报关资料和运营资料整合到 SKU 详情弹窗内，通过 Tab 分组切换，一个入口完成所有维度信息维护。
2. **产品线管理**：新增产品线一级菜单，支持创建、编辑和归档产品线；SKU 归属到产品线，并支持按产品线聚合统计。
3. **品牌管理**：新增品牌一级菜单，维护品牌名称、LOGO、所属国家等信息，支持 SKU 关联品牌。
4. **资质管理**：新增资质一级菜单，维护产品认证资质名称、编号、有效期和附件，支持 SKU 关联资质，并在资质到期前预警。

### 1.3 捆绑销售管理

**业务目标**

通过建立虚拟捆绑 SKU（套装 SKU）概念，解决同一套装在多平台分散映射不同 SellerSKU 导致销量无法聚合统计的问题，为备货计划和采购计划提供准确的套装维度销量数据。

**1.0 现状**

1. **无虚拟捆绑 SKU 概念**：当前中台只有实物 SKU，没有套装/捆绑 SKU 的定义，无法表达“焊机 + 焊帽 + 焊条”这类组合套装的产品关系。
2. **套装销量分散统计**：同一个套装在不同平台映射了不同的 SellerSKU，例如 SellerSKU A、SellerSKU B、SellerSKU C，三个平台分别统计销量，运营无法直接看到该套装全平台总销量，需要手动汇总后再做备货和采购，效率低且容易出错。

**2.0 规划**

1. **新增捆绑 SKU 管理**：创建虚拟捆绑 SKU，定义套装包含的实物 SKU 及各自数量。
2. **多平台 SellerSKU 映射**：将同一捆绑 SKU 与多个平台的 SellerSKU 建立映射关系，实现跨平台套装归属。
3. **套装销量聚合**：订单销售数据按捆绑 SKU 维度自动聚合，直接展示某套装全平台总销量，为备货计划和采购计划提供数据支撑。

### 1.4 海外仓 SKU 映射

**业务目标**

通过将海外仓 SKU 与 FNSKU 映射能力从仓库管理迁移到产品管理模块，简化维护流程；同时补齐 FNSKU 映射，支撑发货预报自动引用编码和海外仓库存精确管理。

**1.0 现状**

1. **海外仓 SKU 维护入口错位**：当前海外仓 SKU 维护功能放在“仓库管理”模块下，但海外仓 SKU 本质上是产品编码的延伸映射，维护时需要对照产品信息，放在仓库管理导致路径深、操作繁琐。
2. **缺少 FNSKU 映射**：第三方海外仓 SKU 编码有维护入口，但亚马逊 FBA 专用的 FNSKU 映射完全缺失。发 FBA 单时运营需要临时去卖家后台查找并手动填入，库存管理也无法精确到 FNSKU 维度，容易出现本地 SKU 库存正确但 FNSKU 维度不一致的问题。
3. **操作流程复杂**：现有海外仓 SKU 维护步骤繁琐，添加一个 SKU 的海外仓编码需要多次页面跳转，批量维护时效率低。

**2.0 规划**

1. **入口迁移**：将海外仓 SKU 维护从“仓库管理”迁移到“产品管理”，与本地 SKU 信息合并展示，缩短维护路径。
2. **补齐 FNSKU 映射**：在产品管理模块新增 FNSKU 映射入口，支持按亚马逊站点维护本地 SKU 与 FNSKU 的对应关系。
3. **简化操作流程**：在 SKU 详情弹窗内直接维护海外仓 SKU 和 FNSKU 映射，一个入口完成所有编码维护。
4. **发货预报自动引用**：发货单入库预报时，根据目标海外仓和站点自动带出映射后的海外仓 SKU/FNSKU，无需手动查填。
5. **库存对账校验**：海外仓库存同步时按映射关系自动匹配本地 SKU，支持按海外仓 SKU/FNSKU 维度精确查询库存。

### 1.5 敏感字段与审批流程管理

**业务目标**

建立敏感字段权限和审批流程配置能力，按角色控制敏感信息展示范围；将审核按钮权限与实际审批人、审批层级分离，确保多级审核按既定流程执行。

**1.0 现状**

1. **敏感字段无管控**：采购价格、供应商联系方式等敏感信息未按角色控制，存在非必要人员可见的风险。
2. **审批流程不规范**：当前仅通过审核按钮权限控制审核操作；单据涉及多级审核时，拥有该按钮权限的人员均可审核，无法限定当前审核节点、审核人和审核顺序。

**2.0 规划**

1. **敏感字段权限**：维护敏感字段清单，按角色配置字段可见、脱敏或隐藏；未授权人员不可查看完整内容，也不可通过导出获取。
2. **审批流程设置**：按单据类型配置审批流程，支持设置审批节点、审批人或审批角色、审批顺序及条件；支持多级审核、退回和重新提交。
3. **权限与流程分离**：角色权限仅控制是否具备相关菜单和操作入口；单据进入审批后，只有当前审批节点匹配的待审批人员可以执行审核，不再因拥有审核按钮权限即可审核任意单据。
4. **审批记录追溯**：记录发起人、各节点审批人、审批意见、审批时间、退回原因和流程状态，并关联至原始单据。

## 二、界面与通用能力优化

### 2.1 视觉规范与组件库

**业务目标**

统一中台页面的视觉风格和基础交互，提升整体美观度与使用体验。

**1.0 现状**

当前中台页面整体美观度不足，字号、圆角、间距等缺少统一规范，不同页面的视觉和交互风格不一致。

**2.0 规划**

1. 统一调整中台页面 UI 风格，包括字号、颜色、圆角、间距、按钮、表格、弹窗和提示反馈等。
2. 支持主题色配置，统一全系统主色及相关状态颜色。

### 2.2 账号管理与飞书登录

**业务目标**

以飞书作为中台员工身份的唯一来源，建立一人一账号的账号体系，替代开发人员直接操作数据库创建、关闭账号的方式，实现员工身份可识别、账号生命周期自动同步和操作记录可追溯。

**1.0 现状**

1. **账号依赖开发维护**：账号创建、关闭需要开发人员直接操作数据库，业务管理员无法自行维护，账号生命周期没有标准流程。
2. **身份无法准确识别**：当前缺少一人一账号的身份体系，新增、修改、删除、审核和导出等操作无法稳定追溯到具体人员。
3. **未对接飞书登录**：中台未接入飞书，员工不能通过飞书扫码登录；如使用手机号登录，还需额外维护中台账号和密码。

**2.0 规划**

1. **飞书登录**：公司飞书组织内的员工支持通过飞书扫码或授权登录中台，无需单独注册和维护中台密码。
2. **手机号登录**：如需提供手机号登录，中台通过短信验证码验证手机号后，再匹配飞书员工及在职状态；手机号仅用于身份匹配，不能直接作为飞书登录凭据。
3. **账号自动同步**：同步飞书人员的新增、变更、冻结和离职状态；新员工自动创建或激活中台账号，离职、冻结人员自动禁用中台账号及登录会话。
4. **账号唯一标识**：中台账号与飞书用户唯一标识绑定，不以姓名或手机号作为唯一账号依据；同步姓名、头像、手机号等基础资料供展示和检索。
5. **操作身份统一**：所有新增、修改、删除、审核、导出等操作绑定到具体中台账号，支持按人员、时间和业务单据追溯操作记录。

### 2.3 部门管理与飞书组织同步

**业务目标**

同步飞书组织架构、部门和直属上级关系，建立中台统一的人员组织关系，为单据审核、消息推送、数据查询和部门维度统计提供准确依据。

**1.0 现状**

1. 中台没有独立的部门管理和组织层级，账号无法关联所属部门、部门负责人和直属上级。
2. 无法查询员工上级所在部门及直属上级，单据审核无法准确推送至对应负责人，只能依赖线下确认或固定人员配置。
3. 人员调岗、部门调整和上级变更无法自动同步，组织关系容易过期，影响审核流转和数据归属。

**2.0 规划**

1. **组织架构同步**：同步飞书组织、部门、父子部门关系、部门负责人和部门启停状态，形成中台部门树。
2. **人员部门关系同步**：同步员工所属部门，支持一名员工关联多个部门；中台不得默认将某一个部门作为唯一归属部门。
3. **直属上级关系同步**：同步员工直属上级；同时保留部门负责人信息，明确区分“直属上级”和“部门负责人”两种关系。
4. **审核路由支撑**：审核流程可按单据发起人的直属上级配置审核人或消息推送对象；直属上级缺失、离职或无权限时，进入待处理异常并按预设规则处理。
5. **同步机制**：飞书组织、部门、人员和直属上级发生变化时及时同步；同时定期校验，避免因同步失败导致中台组织关系不准确。

### 2.4 角色管理与数据权限

**业务目标**

建立角色、功能权限和数据权限体系，使不同岗位仅能访问职责范围内的业务和数据；角色基于已同步的飞书账号和部门进行分配，但角色定义及业务权限仍由中台统一管理。

**1.0 现状**

1. **无统一角色体系**：账号、岗位和业务权限未建立规范关系，无法按角色统一配置菜单、操作和数据范围。
2. **无店铺及业务数据隔离**：当前不同账号可见数据范围基本一致，无法满足“运营只看自己负责店铺单据”等基本要求，存在数据泄露风险。
3. **无敏感字段管控**：供应商名称、地址、联系方式、采购价格等敏感字段未做权限控制，所有有账号的人都可查看。

**2.0 规划**

1. **角色定义**：支持维护业务角色及其菜单、按钮、接口、审核、导出和字段权限；角色不由飞书自动创建或修改。
2. **账号与部门授权**：管理员可向已同步的飞书账号直接分配角色，也可按部门批量配置默认角色；账号、部门或角色变更后及时生效并保留变更记录。
3. **数据范围管理**：支持按团队、平台、店铺、仓库、国家/站点等维度配置角色数据范围；未授权的单据、订单、库存等数据对用户不可见。
4. **敏感字段权限**：维护敏感字段清单，例如供应商名称、地址、联系方式、采购价格等；按角色或账号配置可见范围，未授权字段脱敏或隐藏。
5. **权限与审计**：记录角色分配、权限变更、敏感字段查看、数据导出和高风险业务操作，满足问题追溯和合规审计要求。

### 2.5 账号安全与登录会话管理

**业务目标**

在独立账号基础上，加强登录安全和会话管理，确保账号使用人可识别、风险可控制、权限可及时回收。

**1.0 现状**

多人共用账号会导致：

1. 无法确认具体是谁执行了删除、导出、修改等操作，审计不可追责。
2. 一台电脑泄露密码后，其他人的权限会被连带暴露。
3. 员工离职、转岗时无法只撤销个人权限。

**2.0 规划**

1. 每位员工使用独立账号，支持查看登录设备和会话状态。
2. 支持用户退出其他设备，以及管理员强制下线高风险会话。
3. 记录用户、设备、会话和操作之间的关联关系，支持异常登录和高风险操作追溯。

## 三、供应链中台

### 3.1 库存管理

**业务目标**

建设统一库存中心，对业务只提供一套正式库存口径，统一管理库存余额、库存流水、占用和差异处理；打通海外仓、领星和易仓等外部库存结果及流水，为备货、发货、采购和库存对账提供可信的库存依据。

**系统能力**

1. 建立库存余额、库存流水和库存占用三类账本，保证余额、流水和占用明细可相互核对。
2. 建立统一库存变动引擎，集中处理入库、出库、占用、释放、冻结、解冻、调拨、盘点和调整，禁止各业务模块直接修改库存。
3. 建立海外仓、领星、易仓等外部库存结果、库存流水及状态映射能力，支持差异快照、异常流水和团队归属处理。
4. 提供统一库存查询入口，支持按 SKU、仓库、团队、库存状态、占用来源和库存流水查询及下载。

**1.0 现状**

1. **库存口径不统一**：当前库存以初始化导入数据为起点，结合中台可获取的订单出库、发货单收货等动作增减；海外仓调拨、退货上架、报损、盘点及人工调整等业务未完整接入，运行一段时间后中台库存容易与海外仓实际库存产生差异。
2. **存在多套库存认知**：中台逻辑库存与海外仓库存可能并存，供应链难以确定备货、发货和分析应以哪一套数据为准；中台库存同时存在 SKU、仓库、团队、平台、店铺、Seller SKU 等混合粒度，库存领域与销售映射关系未有效拆分。
3. **库存状态和变动机制不规范**：在库、待发、在途、在产等状态命名和边界不清晰，缺少统一的占用、释放、冻结、解冻和调整规则；库存变动无法完整追溯来源单据、外部流水和处理原因。
4. **查询和差异处理能力不足**：供应商库存、自营仓、物流中转仓和海外仓库存分散在多个页面，缺少统一的库存流水、占用明细、差异快照和异常处理入口；库存单位成本和库存金额也尚未形成统一口径。

**2.0 规划**

1. **一套正式库存口径**：中台面向业务只展示一套正式库存。海外仓、领星、易仓等可信外部库存结果及流水接入后，作为对应仓库库存更新的重要依据；中台保留计算结果、同步快照和校验记录用于排查，但不再并列提供两套正式库存余额。
2. **外部库存接口接入**：按“对接一家、验证一家、上线一家”的方式逐步直连主要海外仓；Amazon/FBA 短期通过领星获取库存，已认可使用易仓库存的仓库可先通过易仓同步，无 API 仓库再单独评估过渡方案，不以 RPA 作为主要建设方向。
3. **接口上线库存初始化**：每个海外仓接口上线时，保存切换前后库存及差异快照，以该仓库外部库存结果重新确认仓库 + SKU 总量；再按中台现有团队库存占比进行首次团队分配，并保留一次性调整记录。
4. **团队归属和异常处理**：后续外部流水优先通过订单号、发货单号等外部单据号匹配中台单据和团队；无法匹配团队的调拨、盘盈盘亏和外部调整等流水进入异常池，由业务确认归属并通过正式单据处理。发货单分批上架时，默认按发货单各团队计划数量比例分配，并支持人工调整。
5. **库存基础模型**：国内物理库存以“SKU + 仓库 + 团队/货主”为基础颗粒度，平台、店铺和 Seller SKU 作为销售映射属性，不进入国内物理库存主维度；Amazon FBA 等店铺专属库存场景单独处理。
6. **库存状态与可用量**：统一管理在库、可用、占用、冻结和在途等状态，其中“在库数量 = 可用数量 + 占用数量 + 冻结数量”；采购计划等尚未形成实物的数量作为计划供给管理，不与实物库存混淆。备货、发货等业务以可用库存作为主要判断依据。
7. **库存占用和释放**：库存占用必须关联具体业务单据，记录占用、已执行、已释放和剩余数量；单据完成、取消或作废后，未执行占用自动释放，避免可用库存被长期错误锁定。
8. **统一库存账本与变动类型**：所有采购入库、发货入库、销售出库、调拨、退货、盘盈、盘亏等变动统一生成库存流水，并明确来源单据、业务类型、数量、状态变化和操作记录；库存余额、流水和占用明细可相互核对。
9. **库存差异快照**：中台计算结果与外部库存结果出现差异时，记录对比时间、仓库、SKU、双方数量、差异数量、相关出入库流水、处理状态及原因；实际盘点差异必须通过盘盈、盘亏等正式调整单据修正，不允许无记录直接改数。
10. **库存中心整合**：整合现有分散库存查询页面，形成库存总览、库存明细、库存流水和占用明细等统一视图，支持按 SKU、仓库、团队、状态、来源单据查询及下载。

### 3.2 采购计划与发货计划

**业务目标**

将采购计划和发货计划从“一个 SKU 一张单”的简单记录，升级为结合库存和供应商库存的多 SKU 计划工具；支持从采购缺口识别到提货、调拨和货权调整的执行联动。

**系统能力**

1. 建立采购计划、发货计划的主单和明细模型，一张计划单可包含多个 SKU，并记录每个 SKU 的计划数量、执行数量和剩余数量。
2. 发货计划关联供应商库存、提货数量和调拨数量，支持自动生成跨仓调拨单及关联的货权调整单。

**1.0 现状**

1. **单据结构不合理**：采购计划和发货计划当前均为一个单据对应一个 SKU，无法在同一张单据中处理同一供应商、目的仓或提货批次下的多个 SKU，单据数量多、审批和执行效率低。
2. **采购计划未结合库存**：采购计划不能有效结合当前可用库存、在途库存和待入库数量识别实际采购缺口，容易依赖人工判断并产生重复采购风险。
3. **发货计划缺少库存调度能力**：建立发货计划时无法根据供应商库存判断可提货数量和需调拨至物流中转仓的数量，后续调拨和货权转移需要人工线下处理。

**2.0 规划**

1. **多 SKU 计划单**：采购计划和发货计划均采用“主单 + 多条 SKU 明细”结构，支持按供应商、目的仓、团队、提货批次等条件合并多个 SKU 创建一张计划单，替代“一张 SKU 一张单”。
2. **采购计划执行关联**：采购计划明细支持关联一个或多个采购单，并回写已下单、采购中、部分到货、已完成和剩余待采购数量，避免同一缺口重复下单。
3. **发货计划按供应商库存调度**：创建发货计划时，按 SKU 查询供应商仓库存，区分可直接提货数量、需要从其他仓库调拨至物流中转仓的数量及库存不足数量，为发货安排提供依据。
4. **自动生成调拨和货权调整**：发货计划确认后，针对需要转运至物流中转仓的货物自动生成跨仓调拨单；涉及团队货权变更时，同步生成关联的货权调整单。调拨入库确认后，自动完成对应库存位置和货权归属更新。

### 3.3 采购单完整做到中台

**业务目标**

将采购单完整沉淀在中台，避免易仓、领星和中台分别维护采购单造成数量、成本、入库、库存金额、供应商及付款状态不一致，保证采购、库存、财务和审计数据形成唯一、完整、可追溯的业务链路。

**系统能力**

1. 统一管理采购数量、价格、成本、供应商、交期、入库、返利、付款和账期。
2. 支持同 SKU 比价、采购成本跟踪、SKU 到仓成本和三层毛利成本池核算。
3. 支持采购计划、采购单、入库、发票和付款之间的关联。
4. 支持易仓、领星执行任务同步、结果回传、异常处理和对账，确保采购主单只能在中台维护。

**1.0 现状**

1. 当前采购单统一推送至易仓，易仓收货入库后，属于亚马逊的货物需要再做其他出库，扣减易仓库存。
2. 领星侧再通过其他入库增加亚马逊货物库存，采购业务因此分散在中台、易仓和领星多个系统中。
3. 如果中台、易仓和领星的采购单都可以独立修改，会形成三套采购数量、三套采购成本、三套入库数量、三套库存金额、三套供应商和付款状态。
4. 财务无法准确判断哪一张是真实采购单，发票、合同、付款和入库记录也无法准确对应，后续请款、成本核算、库存核算和审计追溯都存在风险。

**2.0 规划**

1. 采购单统一在中台创建、审核、修改和关闭，中台采购单作为采购业务唯一主单。
2. 易仓、领星不再独立维护采购业务主单，仅根据中台采购单生成执行任务或执行副本，并回传收货、质检和入库结果。
3. 中台统一沉淀采购数量、采购成本、入库数量、库存金额、供应商、发票、付款和采购状态，避免同一采购业务在多个系统重复维护。

**核心原则**

中台采购单是唯一业务主单；易仓和领星是执行系统，不是第二套采购主系统。三套系统可以存在执行记录，但不应存在三张可以独立修改、独立作为财务依据的采购主单。

### 3.4 采购价相关报表

**业务目标**

沉淀历史采购价和价格变动数据，帮助采购、供应链快速识别涨价、降价和异常价格，为供应商谈价、采购决策和成本分析提供依据。

**2.0 规划**

1. 建立历史采购价页面，按 SKU 展示产品、供应商、采购员、采购单、采购日期、本次采购价、上次采购价、采购数量、收货数量和最后收货时间等信息。
2. 自动识别同一 SKU 的采购价格变化，展示涨价金额、降价金额、涨价 SKU、降价 SKU、涨降价次数及价格变化趋势。
3. 支持按供应商、SKU、采购员、采购时间、采购仓库等维度筛选、汇总和下钻，分析各维度的涨降价金额、SKU 数量及采购价格变化明细。
4. 支持同一 SKU 的历史采购价趋势和不同供应商采购价对比，辅助采购比价和供应商谈价。
5. 支持 AI Agent 基于权限范围查询采购数据，例如查询某供应商某时间段涨价金额、近期开价上涨的 SKU、某采购员负责 SKU 的价格变化等，并返回对应明细和统计结果。

### 3.5 亚马逊 FBA 发货单管理

**业务目标**

支持亚马逊 FBA 货件在中台形成对应发货单，统一管理发货仓、供应商仓、海外仓在途及最终接收情况，确保 FBA 发货过程可追踪、库存可核对。

**1.0 现状**

当前发货单不支持亚马逊 FBA 货件。运营虽然会先在亚马逊店铺创建 FBA 货件，但中台没有对应发货单，无法统一管理发货仓出库、供应商仓待发、海外仓在途和最终接收数量，FBA 货件也无法与采购、入库和库存数据完整关联。

**2.0 规划**

1. 支持将亚马逊店铺创建的 FBA 货件同步或录入为中台发货单，关联店铺、站点、FBA 货件、SKU/FNSKU、数量和目的仓。
2. 支持管理发货仓、供应商仓、海外仓在途和 FBA 接收等关键环节。
3. 发货单关联发货计划、采购单、入库批次和库存流水，记录出库数量、在途数量和最终接收数量。
4. 支持部分发货、部分接收、短收等异常情况。

### 3.6 采购对账

**业务目标**

建立统一的采购对账机制，将采购单、入库单、退货单和请款单进行关联，先完成业务对账，再进入财务请款，避免直接请款导致数据不准确、流程不可回退和财务无法追溯。

**系统能力**

1. 建立采购对账单的独立单据模型，记录对账明细、金额、差异、关联单据和处理状态。
2. 支持采购单与入库数量、采购金额、退货数量的核对。
3. 支持对账单提交、审核、退回、重新对账和确认完成，退回时记录原因。
4. 对账确认后生成对应请款单，请款单关联对账单和原始业务单据。

**1.0 现状**

1. **采购对账未上线**：现有采购对账功能较为简单，没有独立的采购对账单，也不支持退回或回退操作，采购单完成后直接进入请款，缺少规范的业务核对环节。
2. 请款单与采购单、入库单、退货单等原始业务数据关联不完整，出现差异时难以定位和追溯。

**2.0 规划**

1. 新增采购对账单，作为采购和请款之间的中间业务单据。
2. 根据采购单、入库单和退货数据核对采购数量及金额，对账确认后再生成请款单。
3. 对账单支持草稿、待审核、已退回、对账完成和已关闭等状态，并支持退回后重新提交。
4. 请款单必须由已确认的采购对账单生成，并保留与原始单据的完整关联关系。

### 3.7 辅料包材管理与库存货权调整

**业务目标**

完善辅料包材和库存货权管理能力，支持辅料包材作为 SKU 进行维护、消耗和成本核算；同时将平台仓、海外仓的货权调整规范为独立单据，确保库存数量、货权归属和成本变动可追溯。

**系统能力**

1. 支持维护辅料包材 SKU、消耗数量、配比和单价，并自动计算辅料包材成本。
2. 支持记录辅料包材的实际消耗数量和消耗成本，按 SKU 进行统计。
3. 建立货权调整单，记录调整 SKU、仓库、来源团队、调入团队、调整数量、调整原因和处理状态。
4. 货权调整单完成后同步更新库存归属，并生成对应的库存流水。

**1.0 现状**

1. 当前未完整支持辅料包材 SKU、数量配比、单价及成本核算，库内加工时无法准确记录辅料包材的消耗数量和成本。
2. 当前平台仓、海外仓的货权调整缺少独立单据，调整过程和库存归属变更缺少规范记录，无法完整追溯。

**2.0 规划**

1. 新增辅料包材 SKU 管理，维护辅料包材与产品之间的数量配比、单价和成本。
2. 库内加工或相关业务发生辅料包材消耗时，自动扣减对应库存，并记录消耗数量和成本。
3. 新增库存货权调整单，支持平台仓、海外仓在不同团队之间进行货权调整。
4. 货权调整单支持草稿、提交、完成和作废等状态，完成后同步更新库存归属并记录库存流水。

### 3.8 跨仓调拨

**业务目标**

建立规范的跨仓调拨流程，统一管理供应商仓、本地仓和物流中转仓之间的库存转移，记录调出、在途、调入和差异处理全过程，替代技术人员直接修改库存的临时处理方式，确保调拨业务有单据、有流水、可追溯。

**系统能力**

1. 建立跨仓调拨单，记录调拨类型、调出仓、调入仓、货主/团队、SKU、申请数量、实际出库数量、实际入库数量和差异数量。
2. 支持调拨审核、出库、调拨在途、部分入库、完成、作废和反向调拨等状态与操作。
3. 根据调拨状态自动更新调出仓占用库存、调拨在途库存和调入仓可用库存，并生成完整的库存流水。
4. 支持调拨单关联发货计划、发货单和采购单，用于追溯调拨原因、库存来源和后续发货去向。
5. 支持调拨短少、破损、错货、多收和部分到货等异常处理，保留原因、凭证和处理记录。

**1.0 现状**

1. 当同一 SKU 分散在供应商仓、本地仓和物流中转仓，需要集中到同一发货仓时，中台没有仓库之间的调拨单，无法按正常业务流程完成库存转移。
2. 目前只能由业务人员线下整理调拨表格，再由技术人员直接扣减调出仓库存、增加调入仓库存，缺少正式单据、调拨在途和库存流水。
3. 调拨过程中发生部分出库、部分入库、运输短少或破损时，系统无法记录实际数量和差异责任。
4. 技术人员直接修改库存后，无法准确追溯调拨发起人、出库确认人、入库确认人和调拨原因，容易造成库存不一致，并影响发货履约、采购对账和异常责任追溯。

**2.0 规划**

1. 新增跨仓调拨单，支持一张调拨单包含多个 SKU，并统一记录调出仓、调入仓、货主/团队、调拨原因、预计到达时间和物流信息。
2. 调拨单支持“草稿、待审核、待出库、调拨在途、部分入库、已完成、已驳回、已作废”等状态，支持分批出库和分批入库。
3. 审核通过后占用调出仓库存；确认出库后扣减调出仓库存并增加调拨在途；确认入库后减少调拨在途并增加调入仓可用库存。
4. 调拨申请数量、实际出库数量和实际入库数量分别记录，数量不一致时生成调拨差异，经确认处理后才能完结。
5. 支持从发货计划或发货单生成调拨需求，并回写已调拨、调拨在途和已到仓数量，货物到达目标发货仓后再进入发货环节。
6. 调拨单默认只改变库存位置，不改变团队和货权归属；涉及团队归属变更时，通过货权调整单单独处理。
7. 供应商尚未正式交付或调入公司仓时才发生货权转移的场景，应通过采购收货处理，不得使用普通调拨规避采购入库和采购对账。
8. 记录创建、审核、出库、入库、驳回、作废和反向调拨的操作人、操作时间及修改前后数据，满足库存对账和审计追溯要求。

### 3.9 入库单管理

**业务目标**

建立统一的入库业务凭证，承接采购收货、提货到仓、跨仓调拨入库等业务，解决当前采购单收货后没有独立入库单、库存增加缺少单据依据的问题，实现入库数量、库存变化和来源单据可追溯。

**系统能力**

采购单负责记录“采购了什么”，入库单负责记录“实际入库了什么”。入库单关联来源单据、入库仓库、货主/团队、SKU、批次及实际入库数量，并驱动库存和来源单据状态更新。

**1.0 现状**

1. 采购单收货后直接增加库存，没有生成独立入库单，缺少正式的库存入账凭证。
2. 无法完整记录分批到货、少货、多货和破损等实际收货差异。
3. 提货、运输和入库的业务边界不清晰，容易将提货数量直接作为实际入库数量。
4. 采购对账缺少明确的实际入库数量依据，库存变动也难以追溯到具体业务单据。

**2.0 规划**

1. 新增入库单列表和详情，支持采购入库、调拨入库、退货入库和其他入库等类型。
2. 采购单支持生成入库单，一张采购单可以根据分批到货情况生成多张入库单。
3. 入库单记录预计数量、实际入库数量、合格数量、破损数量、少货数量和多货数量。
4. 供应商提货后先进入在途状态，货物到达目标仓并确认收货后，再完成入库并增加库存；提货操作本身不直接增加库存。
5. 跨仓调拨到达目标仓后生成或确认调拨入库单，扣减调拨在途库存并增加目标仓库存。
6. 入库完成后，自动更新采购单的已入库数量、未入库数量及到货状态。
7. 采购对账以已确认的采购入库单作为主要数量依据。
8. 入库单保留与采购单、调拨单等来源单据的关联关系，并生成对应的库存流水。
9. 入库完成后不得直接删除或修改；发生错误时通过撤销、红冲或差异调整处理，并保留完整操作记录。

## 四、运营中台

### 4.1 订单结算状态、结算账单与费用账单对接

**业务目标**

通过订单和 SKU 关联账单获取结算、费用数据，再按照分摊规则分摊至 SKU 维度，实现单 SKU 利润核算。

**系统能力**

1. 统一结算、物流、广告和费用账单的数据模型与字段口径，支持 RPA 或接口接入。
2. 支持账单清洗、订单/SKU 匹配、费用分摊和异常处理。
3. 支持 SKU 净利润计算、利润台账、数据重算和审计追溯。

**功能范围**

新增账单管理模块，支持按平台、订单、SKU、账期和账单类型维护映射关系及分摊逻辑，并为订单结算状态标记、费用归集和利润核算提供统一数据基础。

**1.0 现状**

账单数据散落在各个平台，结算账单、物流账单和广告账单的字段及口径不统一，财务依赖人工下载、清洗和核算，无法稳定做到单 SKU 利润核算。

**2.0 规划**

1. 将各平台结算账单、物流账单和广告账单统一为标准字段格式，统一数据指标口径，包括数据来源、指标名称、指标定义和计算公式。
2. 通过 RPA 自动登录各平台下载账单，按照统一数据模板进行清洗加工，并将结算账单和费用账单关联到具体订单和 SKU。
3. 建立订单结算状态标记能力，区分未结算、部分结算、已结算和异常等状态，支持按订单和 SKU 查询结算进度。
4. 按照既定分摊规则自动计算每个 SKU 的净利润，并支持分摊结果查看、异常修正和重新计算。
5. 搭建利润台账，按日、周、月自动更新，支持按 SKU、平台、店铺和国家等多维度下钻。
6. 建立订单、SKU、结算账单、费用账单、采购成本和库存成本之间的关联关系，为财务核算、请款和经营分析提供统一数据基础。

# 虚拟 SKU 缺失对订单销量及供应链数据的影响

## 一、问题背景

当前中台没有“虚拟 SKU”概念，系统只能把订单中的 SKU 当作普通商品 SKU 处理。但在电商业务中，平台上销售的商品可能是套装、组合装或赠品组合，平台传入的是一个组合 SKU，仓库实际拣货和采购的却是多个真实商品。

因此，系统需要区分两类数量：

- **销售数量**：客户购买了多少个套装或组合商品。
- **实物需求数量**：仓库实际需要拣货、采购和扣减多少个子 SKU。

如果不区分这两类数量，就会出现销售报表、采购计划、库存数据和发货数据之间无法对账的问题。

## 二、SKU 层级关系

完整的 SKU 关系通常为：

```text
平台 SKU（SellerSKU）
        ↓ 映射
销售主 SKU
        ↓ 组合拆分 / BOM
销售子 SKU
        ↓
发货 SKU
```

### 1. 真实 SKU

真实 SKU 是一个平台 SKU 对应一个实物商品，不需要拆分：

```text
平台 SKU → 销售主 SKU → 销售子 SKU / 发货 SKU
```

销售主 SKU、销售子 SKU和发货 SKU通常是 1:1 关系，库存可以直接扣减主 SKU。

### 2. 虚拟 SKU

虚拟 SKU 是平台销售的组合商品，仓库中不存在一个对应的实物商品，需要拆分成多个子 SKU：

```text
组合 SKU：制冷片三件套
    ├── 子 SKU A：制冷片 × 1
    ├── 子 SKU B：导热硅脂 × 1
    └── 子 SKU C：铝制散热片 × 1
```

如果销售 100 套，实际需求不是 100 个商品，而是：

```text
子 SKU A：100 个
子 SKU B：100 个
子 SKU C：100 个
```

如果某个子 SKU 的组合用量是 2，则实际数量还需要乘以 2。

## 三、对订单 SKU 销量统计的影响

### 1. 套装销量和实物销量混淆

客户购买 100 套组合商品时，正确的销售口径是 100 套；拆分后却会产生 3 条子 SKU 明细，数量合计可能是 300 个。

如果系统没有区分，报表可能把 300 个实物误认为 300 个商品销量，导致销售数据被放大。

### 2. 子 SKU 销量被低估

如果系统只统计平台组合 SKU，子 SKU没有销量记录，那么各个实物商品的真实需求会被隐藏，后续无法据此生成准确的采购计划和补货计划。

### 3. 多平台销量无法统一

不同平台可能使用不同的组合 SKU编码，但实际销售的是同一套商品。如果没有“平台 SKU → 销售主 SKU”的映射，系统无法将多个平台销量归集到同一个内部商品。

### 4. 销量无法支持库存可售计算

组合商品的可售数量由子 SKU共同决定。例如：

```text
子 SKU A 可用 100 个
子 SKU B 可用 80 个
子 SKU C 可用 120 个
```

如果每套各需要 1 个，则最多只能销售 80 套。组合商品的可售量取决于库存最少的子 SKU，而不是各个 SKU 库存简单相加。

## 四、对采购和供应链的影响

| 影响领域 | 具体问题 |
|---|---|
| 采购计划 | 采购计划可能只记录组合 SKU，没有拆出真实采购数量。 |
| 采购单 | 采购单无法准确生成子 SKU明细，供应商收到的采购需求不完整。 |
| 库存扣减 | 系统可能扣减一个仓库中不存在的虚拟 SKU，真实子 SKU库存没有减少。 |
| 补货计算 | 子 SKU实际需求被低估，容易出现缺货或临时采购。 |
| 发货拣货 | 仓库无法仅根据组合 SKU判断需要拣选哪些实物。 |
| 收货核对 | 供应商按子 SKU送货，但中台按组合 SKU收货，数量无法对应。 |
| 在途统计 | 采购数量、已收货数量和在途数量缺少统一的实物口径。 |
| 成本核算 | 组合销售价对应主 SKU，但采购成本发生在多个子 SKU，无法准确分摊。 |

## 五、对当前中台业务链路的影响

### 1. 采购计划

当前采购单正式来源是采购计划。如果采购计划没有拆分虚拟 SKU，那么后续中台采购单即使成功创建，也可能创建出错误的采购明细。

正确链路应该是：

```text
订单销售数量
    → 识别销售主 SKU类型
    → 组合 SKU按 BOM 拆分
    → 生成子 SKU需求数量
    → 汇总采购计划
    → 生成采购单
```

### 2. 领星采购单 / 易仓采购单

对外创建采购单时，应根据实际供应商采购的商品生成明细：

- 真实 SKU：直接创建该 SKU的采购明细。
- 虚拟 SKU：拆分成多个子 SKU明细后再创建采购单。
- 同一个子 SKU如果来自多个组合商品，应先按子 SKU汇总数量，同时保留来源组合 SKU和来源采购计划的关系。

### 3. FBA 和发货计划

平台或 FBA返回的 SKU通常更接近平台侧 SellerSKU，不能直接认为它就是仓库采购 SKU。中台应至少保留：

- 平台 SKU / SellerSKU；
- 销售主 SKU；
- 销售子 SKU；
- 发货 SKU；
- 组合用量；
- 原始销售数量；
- 拆分后的实物数量。

这样才能同时回答两个问题：

- 平台上卖了多少套？
- 仓库实际要准备多少个实物？

## 六、数据统计口径建议

建议保留两套统计口径，不能用一套数量覆盖另一套数量。

| 统计口径 | 统计对象 | 适用场景 |
|---|---|---|
| 销售口径 | 原始平台 SKU / 销售主 SKU | 销量报表、商品排名、销售分析、平台对账 |
| 供应链口径 | 销售子 SKU / 发货 SKU | 采购、库存、补货、拣货、发货和收货 |

核心原则：

```text
销售报表保留“卖了什么”
供应链明细记录“实际需要什么”
```

## 七、最小可行改造方案

当前不一定需要立即建设完整的虚拟 SKU系统，可以先做最小改造。

### 1. 增加 SKU 类型

在商品或 SKU映射中增加：

```text
sku_type = REAL       真实 SKU
sku_type = VIRTUAL    组合 SKU
```

### 2. 增加组合关系表

至少保存以下字段：

| 字段 | 含义 |
|---|---|
| parent_sku | 组合主 SKU |
| child_sku | 子 SKU / 发货 SKU |
| quantity | 每 1 个主 SKU对应的子 SKU数量 |
| effective_start_time | 关系生效时间 |
| effective_end_time | 关系失效时间，可为空 |
| version | BOM版本 |
| status | 启用 / 停用 |

### 3. 保留原始订单明细和拆分明细

不要直接覆盖原始订单 SKU，建议分成两层：

```text
订单原始明细：记录平台实际传入的组合 SKU和销售数量
订单拆分明细：记录拆分后的子 SKU和实际需求数量
```

### 4. 采购和库存使用拆分明细

- 销售分析使用原始订单明细。
- 采购计划使用拆分后的子 SKU明细。
- 采购单使用实际采购 SKU。
- 仓库库存扣减使用发货 SKU。
- 收货和入库结果回写到实际子 SKU。

### 5. 保存 BOM 快照

订单产生时应保存当时使用的组合关系版本。后续如果套装组成发生变化，历史订单仍应按照下单当时的 BOM计算，不能使用最新关系重新拆分历史数据。

## 八、需要提前确认的业务规则

1. 哪些组合商品属于虚拟 SKU，哪些是供应商已经包装好的真实 SKU。
2. 组合 SKU是否允许修改子 SKU组成和用量。
3. BOM发生变化后，历史订单使用旧版本还是新版本。
4. 同一个子 SKU是否允许被多个组合 SKU复用。
5. 组合 SKU的销售数量、子 SKU需求数量、采购数量和库存数量分别展示在哪里。
6. 套装缺少某个子 SKU时，是否允许部分发货或禁止整套销售。
7. 采购计划是否按照子 SKU合并，还是需要保留每个组合 SKU的来源明细。
8. 采购单收货时，是否允许只收部分子 SKU。
9. 平台 SKU、销售主 SKU和发货 SKU之间是否存在一对多、多对一关系。

## 九、结论

没有虚拟 SKU概念时，最容易出现的不是“看不到套装销量”，而是销售、采购、库存和发货各自使用了不同的数量口径，最终无法对账。

建议至少建立以下最小链路：

```text
平台 SKU
    → 销售主 SKU
    → 真实 / 虚拟类型判断
    → BOM拆分
    → 子 SKU / 发货 SKU
    → 采购、库存、发货和收货
```

在完整虚拟 SKU能力建设之前，优先保证“原始销售明细不丢失”和“拆分后的供应链明细可追溯”，这样可以先解决采购和库存准确性问题，再逐步完善销售分析和成本核算。
